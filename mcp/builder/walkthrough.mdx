The lifecycle below is where Builder MCP does more than a thin API wrapper. Branches, variants, environments, and deployments are all first-class tools. You can take an agent from an idea to Live, and roll back if needed, without leaving your MCP client. This is the flow to prompt your assistant through.

<Note>
These steps map to tools in [Capabilities](/mcp/builder/capabilities). You don't call them by hand. Describe the outcome you want and let the client chain the tool calls. Example prompts are shown throughout.
</Note>

## 1. Branch

Never edit a live agent directly. Create a [Branch](/api-reference/agents/introduction) so your changes are isolated until you're ready to publish.

> "Create a Branch of the Acme support agent called `greeting-update`."

## 2. Build

Edit the agent on the Branch: behavior rules, knowledge base topics, connectors, and [variants](/knowledge/variants/introduction) for multi-site configuration.

> "On that Branch, update the greeting and add a knowledge base topic for refund policy."

## 3. Test

Use a [debug chat](/api-reference/debug-chat/introduction) session to exercise the Branch before it goes anywhere. Inspect the resulting [conversation data](/api-reference/conversations/v3/endpoint/get-conversations) to confirm the agent behaves as intended.

> "Start a debug chat against this Branch and ask it about refunds. Show me the transcript."

## 4. Test in Staging (optional)

Move the Branch to Staging to test it on a real phone number or widget, the way a customer would. Staging is available in Branches and Sub-branches modes and holds one Branch at a time. See [Environments](/environments-and-versions/environments).

> "Move the `greeting-update` Branch to Staging."

## 5. Publish to Live

When the Branch looks good, publish it. Its changes are merged onto Live and become the newest version in Live's history. Nothing reaches live callers until this step. In Sub-branches mode, merge a Sub-branch into its Branch first, then publish the Branch.

> "Publish the `greeting-update` Branch to Live."

## 6. Roll back if needed

Every version of Live is kept. If something regresses, [roll back](/api-reference/agents/endpoint/deployments/rollback-to-a-previous-deployment) to a previous version immediately.

> "Roll Live back to the previous version."

## Why this matters

Most MCP servers stop at create-and-update. PolyAI's environments and deployment model mean the whole path runs through the same MCP client you build in: Branch, optional Staging, publish to Live, and roll back if needed. [Variants](/knowledge/variants/introduction) are part of the same flow, so multi-site configuration changes publish with the Branch that contains them.

<Warning>
Publishing and rolling back affect live agents. Gate these behind explicit intent, as described in [Security & safe use](/mcp/builder/security#review-destructive-actions).
</Warning>
