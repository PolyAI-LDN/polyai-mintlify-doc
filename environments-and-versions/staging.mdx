Sandbox has no telephony or API connections, so nothing you build there can reach a real system. That keeps building safe, but it also means you cannot test a real call end to end. Staging is where you do that.

Staging is optional. Most everyday changes go straight from Sandbox to Live, and you only need Staging when you want to hear your agent on a real phone number, or check that it talks to your live APIs correctly.

## What Staging gives you

Staging runs one Branch with a real phone number and real API connections. You call the number, your agent answers from the Branch, and every integration behaves as it will on Live.

<Note>
There is one Staging environment per project today, holding one Branch at a time. Moving another Branch to Staging replaces the one already there, so agree with your team who is using it before you promote. Support for multiple Staging environments is coming soon.
</Note>

## Move a Branch to Staging

<Steps>
  <Step title="Open the Deployments page">
    Find your Branch in the list.
  </Step>
  <Step title="Move it to Staging">
    Use the Branch's actions menu.
  </Step>
  <Step title="Call the Staging number">
    Your agent answers from that Branch, with real API connections behind it.
  </Step>
  <Step title="Publish when you are happy">
    Publishing works the same as it does from Sandbox. Your Branch merges onto Live.
  </Step>
</Steps>

## Editing a Branch that is in Staging

A Branch in Staging is locked for direct editing. This keeps what you are testing stable, so the call you just made is the same agent you are about to publish.

In [Sub-branches mode](/environments-and-versions/sub-branches-mode) you can still change it: make your edit in a Sub-branch and merge that into the Branch. Merges are allowed, direct work on the parent Branch is not.
