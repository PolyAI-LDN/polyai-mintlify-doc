Sub-branches mode is the full model, for several people building updates that ship as one package. It works exactly like [Branches mode](/environments-and-versions/branches-mode), with one extra layer. A Branch can be split further into Sub-branches.

<img className="hidden dark:block" src="/images/deployment/deployment-model-dark.svg" alt="The full model: Branches and Sub-branches in Sandbox, one Branch in Staging, publishing onto Live" style={{ maxWidth: '920px', width: '100%', margin: '0 auto' }} />

## How it works

A Branch is a safe place to work. Branches and Sub-branches live in the [Sandbox](/environments-and-versions/environments) environment, sharing the connections set up there.

Your Branch saves as you go. Test it at any time by running [simulation tests](/testing/simulation-tests), or by talking to your agent over an in-app call or chat. To test on a channel, move the Branch to [Staging](/environments-and-versions/staging).

When you are ready to ship, publish your Branch. It merges onto Live and becomes the newest version in Live's history.

Sub-branches exist so several people can work together on an update that ships as a package, without treading on each other's toes. Each person works in their own Sub-branch, an isolated copy that only ever merges back into its parent Branch. As pieces finish, the team merges them into the Branch and tests everything together before publishing. Sub-branches keep the same sync rules with their parent Branch that Branches keep with Live.

<Frame caption="A Branch expanded to show its Sub-branches, on the Deployments page">
  <img src="/images/deployment/deployments-sub-branches-list.png" alt="Deployments page showing a Branch with two Sub-branches nested under it, and a count of its Sub-branches" style={{ maxWidth: '720px', width: '100%', margin: '0 auto', display: 'block' }} />
</Frame>

The navigation bar at the top shows where you are and allows you to switch between Live, Branches and Sub-branches.

<Tip>
**Publishing merges, it does not replace.** If Live has moved on since you created your Branch, it is marked **Out of sync**. Sync to pull in the latest changes. If you have both edited the same thing, a conflict screen lets you choose which edit to keep. Nothing is silently lost.
</Tip>

## Work on an update with several people

For an update several people work on together and ship as one.

<Steps>
  <Step title="Create a single shared Branch">
    One Branch for the whole piece of work.
  </Step>
  <Step title="Each person creates a Sub-branch">
    Every Sub-branch comes off that shared Branch.
  </Step>
  <Step title="Make your changes">
    Each person works in their own Sub-branch. It saves as you go.
  </Step>
  <Step title="Test each Sub-branch">
    Run tests on a Sub-branch to check its changes in isolation before merging.
  </Step>
  <Step title="Merge each Sub-branch back">
    Merge into the parent Branch as each piece is finished.
  </Step>
  <Step title="Test the Branch">
    Test all the changes together.
  </Step>
  <Step title="Move to Staging (optional)">
    Move the Branch to [Staging](/environments-and-versions/staging) from its actions menu on the Deployments page, then test through the channel you need.

    <Tip>
    Skip this step unless you need to test on a channel.
    </Tip>
  </Step>
  <Step title="Publish">
    Publish the Branch. Everything lands on Live at once.
  </Step>
</Steps>

If the work can ship independently, skip Sub-branches. Each person creates their own Branch and publishes on their own schedule, exactly as in [Branches mode](/environments-and-versions/branches-mode).

<Warning>
Branches cannot merge into each other. Each one publishes to Live on its own.
</Warning>

## Handle an out of sync Branch or Sub-branch

This happens whenever a colleague publishes onto Live before your Branch does, or merges into the parent Branch before your Sub-branch does. Publishing is blocked until you sync.

<Frame caption="Publishing is unavailable until the Branch is synced with Live">
  <img src="/images/deployment/publish-menu-out-of-sync.png" alt="Publish menu on an out of sync Branch, with Publish greyed out and labelled Sync with live first" style={{ maxWidth: '720px', width: '100%', margin: '0 auto', display: 'block' }} />
</Frame>

<Steps>
  <Step title="Your Branch is marked Out of sync">
    This is expected, not an error.
  </Step>
  <Step title="Sync">
    This pulls the latest changes from the parent into your working copy.
  </Step>
  <Step title="Resolve any conflicts">
    If you have both edited the same thing, a conflict resolution screen asks which edit to keep.
  </Step>
  <Step title="Test, then merge">
    Check the merged result before you merge or publish.
  </Step>
</Steps>

<Warning>
The same sync rules apply between a Branch and Live, and between a Sub-branch and its parent Branch.
</Warning>

## When someone publishes while Sub-branches are still open

Nothing is lost. Any Sub-branch still open at that point moves to sit directly under Live and becomes a Branch in its own right. Carry on working, then publish it like any other Branch.

## Compare your changes

Before you publish or merge, open the **Publish** menu and choose **Compare changes** to see your Branch against Live, or your Sub-branch against its parent Branch, side by side. Use it to confirm only your intended change is present.

For how to read a comparison, see [Compare changes](/environments-and-versions/diffs).

## Roll back Live

<Steps>
  <Step title="Open Live's version history">
    Every publish is a version there.
  </Step>
  <Step title="Select a previous version and roll back">
    Live returns to that version in one step.
  </Step>
</Steps>

<Tip>
Because publishing merges rather than replaces, a rollback cannot be silently undone by someone else's publish.
</Tip>
