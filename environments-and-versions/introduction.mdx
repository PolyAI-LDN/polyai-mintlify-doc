Every project has a **Live** version, the agent actually talking to your customers. You never edit Live directly. Instead you create a **Branch**, your own working copy branched off Live, so you start from what is actually running.

## Terminology

| **Term** | **Description** |
|---|---|
| **Live** | The environment serving your customers. You never edit it directly. Publishing merges changes onto it, and each publish creates a new version in its history. You can roll back to any previous Live version. |
| **Branch** | An isolated copy of your agent, branched off Live. Publishing merges it back onto Live. |
| **Sub-branch** | An isolated copy of your agent, branched from a Branch. It only ever merges back into its parent Branch. |
| **Sandbox** | The environment where every Branch and Sub-branch lives while you work on it. It has no telephony or API connections, so nothing you build here can reach a real system. |
| **Staging** | An optional environment where you can test any Branch with a real phone number and API connections, one Branch at a time. |
| **Out of sync** | Your Branch or Sub-branch is behind its parent. Pull the parent's changes in before you can merge. |

## How it works

### Overview

A Branch is a safe place to work. Branches and Sub-branches live in the Sandbox environment, which has no API or telephony connections, so nothing you build can reach a real system. Your Branch saves as you go, and you can test it at any time by running [simulation tests](/testing/simulation-tests) or by talking to your agent over an in-app call or chat. If you want to test with a real phone number and API connections, move it to Staging. When ready, publish: Your Branch merges onto Live and becomes the newest version in Live's history.

A Branch can be split further with Sub-branches. They exist so several people can work together on an update that ships as a package, without treading on each other's toes. Each person works in their own Sub-branch, an isolated copy that only ever merges back into its parent Branch. As pieces finish, the team merges them into the Branch and tests everything together before publishing. Sub-branches keep the same sync rules with their parent Branch that Branches keep with Live, and if someone publishes a Branch while its Sub-branches are still open, that work is not lost. The open Sub-branches move to sit directly under Live and become Branches in their own right.

The navigation bar at the top shows where you are and allows you to switch between Live, Branches and Sub-branches.

Publishing does not have to be a leap of faith. If anything goes wrong, Live rolls back to any previous version in one step.

<Note>
**Publishing merges, it does not replace.** If Live has moved on since you created your Branch, perhaps because a colleague published first, your Branch is marked **Out of sync**. Syncing pulls the latest changes from Live into your Branch. If you have both touched the same thing, a conflict screen lets you decide which edit to keep. Nothing is silently lost.
</Note>

### Make a small change

The everyday case: a knowledge update, a settings change, a prompt tweak.

<Steps>
  <Step title="Create a Branch from Live">
    It branches off the current Live version, so you start from what is actually running.
  </Step>
  <Step title="Make your change">
    It saves as you go.
  </Step>
  <Step title="Test it">
    Run [simulation tests](/testing/simulation-tests) on the Branch, or talk to the agent yourself over an in-app call or chat.
  </Step>
  <Step title="Publish">
    The changes in your Branch merge onto Live and become the newest version in Live's history.
  </Step>
</Steps>

Nothing else rides along with your change, and nobody else's work is touched.

### Test in Staging

Use Staging when in-app testing is not enough, for example when you want to test with a real phone number and API connections. Any Branch can move into Staging, though only one can be there at a time.

<Steps>
  <Step title="Create your Branch and make the change">
    Exactly as above.
  </Step>
  <Step title="Move the Branch to Staging">
    Use the Branch's actions menu on the Deployments page, then call the number.
  </Step>
  <Step title="Publish when you are happy">
    Staging is optional. A Branch can publish straight to Live once you have tested it.
  </Step>
</Steps>

### Work on an update with several people

For a feature several people build together and ship as one.

<Steps>
  <Step title="Create a single shared Branch">
    One Branch for the whole piece of work.
  </Step>
  <Step title="Each person creates a Sub-branch">
    Every Sub-branch comes off that shared Branch.
  </Step>
  <Step title="Test each Sub-branch">
    Run tests on a Sub-branch to check its changes in isolation before merging.
  </Step>
  <Step title="Merge each Sub-branch back">
    Merge into the parent Branch as each piece is finished.
  </Step>
  <Step title="Test the Branch, then publish">
    Test all the changes together, then publish. Everything lands on Live at once.
  </Step>
</Steps>

If the work can ship independently, skip Sub-branches. Each person creates their own Branch and publishes on their own schedule. Nobody queues behind anyone. While one team spends weeks building a new flow in their Branch, a colleague can open a small Branch of their own, update the knowledge base, and publish the same day without touching the team's work.

<Warning>
Branches cannot merge into each other. Each one publishes to Live on its own.
</Warning>

### Handle an out of sync Branch

This happens whenever a colleague merges to the parent before you do.

<Steps>
  <Step title="Your Branch is marked Out of sync">
    This is expected, not an error.
  </Step>
  <Step title="Sync">
    This pulls the latest changes from the parent into your Branch.
  </Step>
  <Step title="Resolve any conflicts">
    If you have both edited the same thing, a conflict resolution screen asks which version to keep.
  </Step>
  <Step title="Test, then merge">
    Check the merged result before you merge or publish.
  </Step>
</Steps>

The same sync rules apply between a Branch and Live, and between a Sub-branch and its parent Branch.

### Roll back Live

<Steps>
  <Step title="Open Live's version history">
    Every publish is a version there.
  </Step>
  <Step title="Select a previous version and roll back">
    Live returns to that version in one step.
  </Step>
</Steps>

Because publishing merges rather than replaces, a rollback cannot be silently undone by someone else's publish.

### When someone publishes while your Sub-branches are open

Nothing is lost. Any Sub-branch still open at that point moves to sit directly under Live and becomes a Branch in its own right. Carry on working, then publish it like any other Branch.

### Compare before you publish

You can compare any two versions side by side to confirm only your intended change is present. See [Compare versions](/environments-and-versions/diffs).
