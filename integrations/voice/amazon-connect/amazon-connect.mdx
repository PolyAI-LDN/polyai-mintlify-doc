![connect-flow](/images/integrations/amazon/connect-flow.png)

Use the [Amazon Connect integration](https://aws.amazon.com/marketplace/pp/prodview-rwoh2vu3mruba?sr=0-1&ref_=beagle&applicationId=AWSMPContessa) to connect PolyAI voice agents to your Amazon Connect instance. You set it up from a guided setup in Agent Studio, then run a PolyAI CloudFormation stack in your own AWS account.

## How the integration works

Amazon Connect transfers the call to a PolyAI number over the phone network (PSTN). PolyAI reads and updates the contact attributes through an IAM role in your AWS account.

![connect-diagram](/images/integrations/amazon/diagram.png)

1. **Claim a number**: your contact flow invokes the `PolyAIWriteContactAttributesToDDB` Lambda function. It claims a free number from the pool of PolyAI numbers you picked, and saves it as the `ExternalPolyNumber` contact attribute. PolyAI matches each call to its contact by the number dialed, so two calls on their way to PolyAI never share a number.
2. **Transfer to PolyAI**: the flow transfers the call to that number. PolyAI reads the contact attributes, so the agent has the caller's context.
3. **Conversation**: the PolyAI agent greets the caller and runs its flows, such as identity verification or information collection.
4. **Hand back**: before hanging up, PolyAI sets the `should_transfer` contact attribute to `true` or `false`. The contact flow resumes and routes on it: to an agent queue, or to end the call.

<Note>
  Only one telephony integration can be connected to a project at a time. If the project already has another one connected, the Amazon Connect setup shows **Another telephony integration is connected** and does not start.
</Note>

### How numbers are reused

A call holds its number only until PolyAI answers, not for the whole conversation.

1. The Lambda function shuffles the numbers in your pool and tries each one with a conditional write to the `PolyAIConnectContactAttributes` DynamoDB table. The write only succeeds if the number has no record, or its record has expired. The first number that succeeds goes to the call, and the record stores the contact's details.
2. When the PolyAI agent answers the transferred call, its start function looks up the record by the number dialed, reads the contact's details, and deletes the record. The number is free again, even while the first conversation continues.
3. If the record is never deleted, for example because the transfer failed, the number frees when the record expires. The `DDBRecordTTL` stack parameter sets the expiry time, in seconds.

So the pool needs enough numbers for the calls Connect transfers at about the same moment, not one for every call in progress. If every number is held, the function keeps trying until PolyAI answers a held call and releases its number, or until the function times out. A record that expires during those retries doesn't free its number for that call. The `WriteContactAttributesToDDBLambdaTimeout` stack parameter sets the timeout, 3 seconds by default. If the function times out, the flow takes the error branch of the **Invoke AWS Lambda function** block. Ask your PolyAI contact how many numbers to add for your traffic.

## Before you start

- An active Amazon Connect instance, and access to the AWS console with permission to create a CloudFormation stack and IAM resources in that account.
- At least one PolyAI number in the project. If you don't have one, buy one first from **Add number** → **Buy Twilio number** in the **Telephony** tab.
- Enough numbers for the calls Connect transfers to PolyAI at about the same moment. A number is free again once PolyAI answers. See [How numbers are reused](#how-numbers-are-reused).
- If your security team reviews the access PolyAI gets, see [What PolyAI changes in your AWS account](#what-polyai-changes-in-your-aws-account).

## Set up Amazon Connect in Agent Studio

Go to **Integrations** → **Telephony** and click **Add number**. In the **Add a number** panel, under **Integrate with your contact center platform**, select **Amazon Connect**. The **Amazon Connect setup** opens.

<Note>
  If the Amazon Connect option shows **Coming soon**, contact your PolyAI account manager.
</Note>

<Steps>
  <Step title="Instance">
    Under **Your Amazon Connect instance**, fill in:

    - **Instance ARN**: in the AWS console, open Amazon Connect and copy the [ARN](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference-arns.html) of your instance. It looks like `arn:aws:connect:us-east-1:123456789012:instance/00000000-0000-0000-0000-000000000000`. Once the ARN is valid, the setup shows the region and AWS account it found. Both are used for the rest of the setup.
    - **PolyAI numbers Connect transfers to**: select the project numbers Connect can transfer calls to. Each option shows the number and its environment. The PolyAI stack gives each transferred call a free number from this pool, and the number frees once PolyAI answers. See [How numbers are reused](#how-numbers-are-reused). Select at least one.

    Click **Next**. PolyAI saves the connection and prepares a CloudFormation link for your account. From here you can't go back to change the instance.
  </Step>

  <Step title="AWS stack">
    Under **Run the PolyAI stack in AWS**, you create the DynamoDB table, Lambda function and IAM roles the integration uses, including the role that lets PolyAI read and update contact attributes on your instance. See [What PolyAI changes in your AWS account](#what-polyai-changes-in-your-aws-account) for what each one does and what PolyAI can access.

    1. Click **Open in AWS console**. CloudFormation opens in your AWS console with the template and every parameter already filled in.
    2. Tick the acknowledgement that the stack creates IAM resources, then create the stack.
    3. Wait for the stack to reach `CREATE_COMPLETE`. It usually takes under a minute.

    The step also shows copy buttons for the **Stack name** and **Template URL**, if you'd rather create the stack yourself.

    Back in Agent Studio:

    - **IAM role ARN** is prefilled from your instance. Change it only if you renamed the role when you created the stack, or if you [use your own IAM role](#use-your-own-iam-role).
    - Tick **The stack reached CREATE_COMPLETE**.

    Click **Finish setup**. You see **Amazon Connect setup submitted**.

    If the link doesn't load, you see **Couldn't build the AWS link**. Click **Try again**, or contact PolyAI support.
  </Step>

  <Step title="Reference">
    The last step shows what to build in your contact flow, the **PolyAI numbers Connect transfers to**, and the **Role ARN** and **External ID** PolyAI uses. See [Finish in Amazon Connect](#finish-in-amazon-connect).
  </Step>
</Steps>

If saving fails, you see **The setup did not save**. Click the button again to retry, or contact PolyAI support if it keeps failing.

### While PolyAI finishes the connection

After you finish setup, your side is done. PolyAI completes its own setup and lets you know when calls can flow, usually within one business day:

1. PolyAI grants itself access to the role you created, using the external ID.
2. PolyAI confirms the numbers are reachable from your instance.
3. You're told when the connection is live.

Until then:

- The **Telephony** tab shows **Amazon Connect setup is pending**. Click **View setup** to review what you submitted.
- **Amazon Connect** shows as **Pending** in the **Add a number** panel.
- If you closed the setup before ticking **The stack reached CREATE_COMPLETE**, opening it again takes you back to the **AWS stack** step.

You can build the contact flow while you wait.

## Finish in Amazon Connect

Build or update the contact flow that should send calls to PolyAI. First, [add the `PolyAIWriteContactAttributesToDDB` Lambda function to your instance](https://docs.aws.amazon.com/connect/latest/adminguide/connect-lambda-functions.html#add-lambda-function), so the flow can invoke it.

1. **Set the caller context.** Set any contact attributes the PolyAI agent needs.
2. **Invoke the Lambda function.** Add an **Invoke AWS Lambda function** block that calls `PolyAIWriteContactAttributesToDDB`. It claims a free PolyAI number for the call and saves it as the `ExternalPolyNumber` contact attribute. Don't hard-code a number.
3. **Transfer to PolyAI.** Add a **Transfer to phone number** block. Set the number dynamically from the `ExternalPolyNumber` contact attribute (namespace **User Defined**). Set **Resume flow after disconnect** to **Yes**. Without it, the flow ends at the transfer.
4. **Route on `should_transfer`.** After the transfer, branch on the `should_transfer` contact attribute:
   - `true` or empty: transfer to an agent.
   - `false`: end the call.

   The flow only resumes when PolyAI hangs up with the caller still on the line.
5. **Keep a fallback.** Leave `should_transfer` unset for a PolyAI fallback, so the call still reaches an agent.
6. **Assign a phone number.** Assign the Amazon Connect number your callers dial to the flow, then save and publish it.

![contact-flow-steps](/images/integrations/amazon/contact-flow-steps.png)

<Note>
  Make sure the contact flow handles failures, for example PolyAI being unreachable or the Lambda function failing to set `ExternalPolyNumber`. Route these cases to a fallback, such as a queue or an error message, rather than leaving the caller stuck.
</Note>

### Use an AI assistant for the Connect side

The **Reference** step shows **Have an AI assistant prepare the Connect side**. Click **Copy prompt** and paste it into an AI assistant that can work in your AWS console.

The prompt already includes your instance ARN, number pool, IAM role ARN and external ID. The assistant asks you which contact flow should send calls to PolyAI, which queue handed-off calls go to, and how many calls can run at once. It then builds the contact flow, asks before publishing a flow that takes live calls, and replies with a summary of what it configured.

## Test the integration

Once PolyAI tells you the connection is live:

1. Call the number assigned to your contact flow and check the PolyAI agent answers with the right context.
2. Trigger a handoff and check the call reaches the agent queue.
3. Place several calls at once and check each one reaches the PolyAI agent with the right context.
4. Use Amazon Connect analytics to track call volume, routing and handoffs.

## What PolyAI changes in your AWS account

You create the PolyAI CloudFormation stack in your account, and the stack creates these resources. Each name ends with a suffix made from your PolyAI project ID.

| Resource | Name | Purpose |
|----------|------|---------|
| DynamoDB table | `PolyAIConnectContactAttributes` | One record per call on its way to PolyAI, keyed by the PolyAI number. A record holds the contact's details from Amazon Connect, such as the contact ID, instance ARN, language, queue and the caller's phone number, plus an expiry time. |
| Lambda function | `PolyAIWriteContactAttributesToDDB` | Claims a free number for each call and writes the call's record to the table. See [How numbers are reused](#how-numbers-are-reused). |
| IAM role | `PolyAILambdaRoleToWriteContactToDDB` | The function's execution role. Only the Lambda service can assume it, not PolyAI. |
| IAM role | `PolyAIRoleToReadAndUpdateContactAttributes` | The role PolyAI assumes during calls. Its trust policy requires your setup's external ID. |
| IAM role | `PolyAIRoleToUpdateLambdaCode` | The role PolyAI can assume to update the function's code and configuration. Its trust policy doesn't require an external ID. |

### What each role grants

These are the grants in PolyAI's current template. A stack created from an earlier template grants more until you update it. See [Stacks created from an earlier template](#stacks-created-from-an-earlier-template).

The two roles PolyAI can assume trust both PolyAI AWS accounts, `168609107022` and `471112995218`.

#### `PolyAILambdaRoleToWriteContactToDDB`

- **Can be assumed by:** the Lambda service only, for the function. PolyAI can't assume it.
- **Grants:** `dynamodb:PutItem` on the table. It also lets the function write its logs to CloudWatch Logs, through the AWS managed policy `AWSLambdaBasicExecutionRole`.
- **Used for:** the function adds each call's record to the table.

#### `PolyAIRoleToReadAndUpdateContactAttributes`

- **Can be assumed by:** the PolyAI AWS accounts, and only with your setup's external ID.
- **Grants:** `dynamodb:GetItem` and `dynamodb:DeleteItem` on the table. `connect:GetContactAttributes` and `connect:UpdateContactAttributes` on the contacts in your instance (`<instance-arn>/contact/*`).
- **Used for:** PolyAI uses all four actions during a call:
  - Read and delete the call's record in the table (`dynamodb:GetItem`, `dynamodb:DeleteItem`).
  - Read the contact's attributes (`connect:GetContactAttributes`).
  - Update the contact's attributes, such as `should_transfer` (`connect:UpdateContactAttributes`).

PolyAI also uses this role to check the connection after you finish setup. The check assumes the role and makes one read from the table (`dynamodb:GetItem`).

#### `PolyAIRoleToUpdateLambdaCode`

- **Can be assumed by:** the PolyAI AWS accounts. Its trust policy has no `sts:ExternalId` condition, so PolyAI doesn't need your external ID to assume it.
- **Grants:** `lambda:UpdateFunctionCode`, `lambda:GetFunctionConfiguration` and `lambda:UpdateFunctionConfiguration` on the function. `s3:ListBucket` and `s3:GetObject` on PolyAI's code bucket, where new code for the function comes from.
- **Used for:** PolyAI can update the function's code and configuration through `PolyAIRoleToUpdateLambdaCode`. It does this only to ship PolyAI updates to that function.

A code update replaces the function's code, so it overwrites any changes you made to the code. A configuration update can replace the function's settings, such as its environment variables.

### Stacks created from an earlier template

To check which template your stack uses, open `PolyAIRoleToUpdateLambdaCode` in IAM. If its policy allows `lambda:*`, your stack was created from an earlier template. An earlier template grants:

- **`PolyAILambdaRoleToWriteContactToDDB`:** `dynamodb:*` on the table, and `connect:*` on everything in your instance (`<instance-arn>/*`).
- **`PolyAIRoleToReadAndUpdateContactAttributes`:** 21 DynamoDB actions on the table, including `dynamodb:Scan`, `dynamodb:Query`, `dynamodb:BatchGetItem` and `dynamodb:GetRecords`. The two Connect actions apply to everything in your instance (`<instance-arn>/*`), not only contacts.
- **`PolyAIRoleToUpdateLambdaCode`:** `lambda:*` on the function.

PolyAI uses the same actions with either template. A stack on an earlier template keeps working, so the update is optional.

To move to the current grants, update the stack with PolyAI's current template:

1. Ask PolyAI support for the current template URL.
2. In CloudFormation, open your PolyAI stack and choose **Update**.
3. Choose **Replace existing template**, then paste the template URL as the **Amazon S3 URL**.
4. Keep every parameter value as it is, including `s3KeyPrefix`.
5. On the review page, check that the changes list only the three IAM roles. If the Lambda function is listed, stop and contact PolyAI support, because the update would replace the function's code.
6. Acknowledge that the stack changes IAM resources, and submit.

IAM updates the role policies in place, so calls aren't interrupted. If you use your own IAM role, the stack's roles still need this update. Update your own role's permissions policy yourself, using the policy in [Use your own IAM role](#use-your-own-iam-role).

### What PolyAI commits not to do

PolyAI's policy is that it never:

- Deletes, updates or recreates your CloudFormation stack.
- Edits your contact flows, queues or any other Amazon Connect configuration. It only reads and updates contact attributes.
- Writes records to the table itself. Only the Lambda function does.
- Creates or changes IAM roles or policies.

This list is a policy. The technical limit is what the roles grant, listed in [What each role grants](#what-each-role-grants). PolyAI can update the function's code, and that code runs with the function's execution role, `PolyAILambdaRoleToWriteContactToDDB`. So code PolyAI ships can do anything that role grants: on the current template, add records to the table and write logs. On an earlier template, that role grants more. See [Stacks created from an earlier template](#stacks-created-from-an-earlier-template).

If the setup is deleted on the PolyAI side, the stack and its roles stay in your account until you delete the stack.

## Use your own IAM role

You can create the role PolyAI assumes yourself, instead of using `PolyAIRoleToReadAndUpdateContactAttributes`. You still run the PolyAI stack, because it creates the table and the Lambda function. The role must be in the same AWS account as your Amazon Connect instance.

Your own role doesn't remove the stack's role. The stack still creates `PolyAIRoleToReadAndUpdateContactAttributes`, and PolyAI can still assume it with your setup's external ID. The template has no option to leave it out. That role grants the same four actions as the permissions policy below, on the same resources. The stack also still creates `PolyAIRoleToUpdateLambdaCode`.

**Trust policy.** Trust both PolyAI AWS accounts, `168609107022` and `471112995218`, and require your setup's external ID. This matches the role the stack creates. The external ID is the `polyAIAssignedExternalId` parameter on your stack's **Parameters** tab in CloudFormation. Agent Studio also shows it as **External ID** on the **Reference** step.

```json Trust policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": ["168609107022", "471112995218"]
      },
      "Action": ["sts:AssumeRole"],
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "<your-external-id>"
        }
      }
    }
  ]
}
```

**Permissions.** Allow these four actions, on the table your PolyAI stack created and on the contacts in your instance:

```json Permissions policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["dynamodb:GetItem", "dynamodb:DeleteItem"],
      "Resource": "<table-arn>"
    },
    {
      "Effect": "Allow",
      "Action": ["connect:GetContactAttributes", "connect:UpdateContactAttributes"],
      "Resource": "<instance-arn>/contact/*"
    }
  ]
}
```

Enter the role's ARN in **IAM role ARN** on the **AWS stack** step, before you click **Finish setup**.

<Warning>
  PolyAI's connection check only assumes the role and calls `dynamodb:GetItem`. It doesn't test the other three actions. A role that is missing one of them still connects, then fails during calls. Without `dynamodb:DeleteItem`, PolyAI can't pick up the call's details. Without the Connect actions, it can't read or set contact attributes such as `should_transfer`. Check that the role allows all four actions before you send live calls.
</Warning>

## Chat and messaging handoff

For webchat and SMS conversations, PolyAI escalates to a live agent through the Amazon Connect [Chat API](https://docs.aws.amazon.com/connect/latest/APIReference/API_StartChatContact.html) instead of a call transfer. This is set up separately, under **Integrations > Amazon Connect** in Agent Studio. See [Amazon Connect chat handoff](/integrations/chat/amazon-connect) for the full guide.

| Field | Required | Description |
|-------|----------|-------------|
| `instance_id` | Yes | The Amazon Connect instance ID. |
| `contact_flow_id` | Yes | The contact flow that routes the chat to a queue. |
| `role_arn` | Yes | IAM role PolyAI assumes to call `StartChatContact`. |
| `aws_region` | No | Region of the Connect instance (for example, `eu-west-2`). Overrides the PolyAI worker's default region. |
| `api_url` | No | Override for the Connect API endpoint. |
| `headers` | No | Static headers to include on API calls. |

### When to set `aws_region`

PolyAI's messaging handoff worker uses a default AWS region. If your Amazon Connect instance is in a different region (for example, your worker defaults to `us-east-1` but your Connect instance lives in `eu-west-2`), set `aws_region` on the integration so `StartChatContact` targets the right region. Without this override, the handoff fails with a `ResourceNotFoundException`.

Use the [region code](https://docs.aws.amazon.com/general/latest/gr/connect_region.html) shown in the Amazon Connect console URL (for example, `eu-west-2`, `us-west-2`, `ap-southeast-2`).

```json
{
  "instance_id": "12345678-aaaa-bbbb-cccc-1234567890ab",
  "contact_flow_id": "abcdef12-3456-7890-abcd-ef1234567890",
  "role_arn": "arn:aws:iam::123456789012:role/PolyAIAccessConnect",
  "aws_region": "eu-west-2"
}
```

### IAM trust policy requirements

PolyAI's handoff worker runs on EKS with [IRSA](https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html), which adds session tags to its credentials when chain-assuming your IAM role. Your `PolyAIAccessConnect` role's trust policy must therefore allow both `sts:AssumeRole` **and** `sts:TagSession` from the PolyAI worker account. If `sts:TagSession` is missing, the assume-role step fails before any Connect API call is made.
