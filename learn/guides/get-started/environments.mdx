**Lesson 5 of 6** – Before your agent goes live, you need to understand how deployments work. This is how you test safely – so changes never reach real users until you're ready.

<LessonMeta level={1} difficulty="Beginner" time="15 min" />

Every project has a **Live** version, the agent actually talking to your customers. You never edit Live directly. Instead you work in a **Branch**, your own isolated copy branched off Live, and publish it back when it's ready.

## How it works

<CardGroup cols={3}>
  <Card title="Live" icon="signal-stream">
    Production. The version handling real traffic. Never edited directly.
  </Card>
  <Card title="Branch" icon="code-branch">
    Your isolated copy of the agent, branched off Live. Publishing merges it back.
  </Card>
  <Card title="Sub-branch" icon="code-merge">
    Splits a Branch further, so several people can share one piece of work.
  </Card>
</CardGroup>

Branches and Sub-branches live in the **Sandbox** environment, which has no telephony or API connections, so nothing you build can reach a real system. When you want to test with a real phone number and API connections, move your Branch into **Staging**.

## The flow

```mermaid
flowchart TD
    A[Create a Branch from Live] --> B[Make your changes]
    B --> C[Test in the app]
    C --> D{Need a real phone number?}
    D -->|Yes| E[Move to Staging and call it]
    D -->|No| F{Tests pass?}
    E --> F
    F -->|Yes| G[Publish onto Live]
    F -->|No| B
    G --> H[Monitor first calls]
```

Publishing **merges** your Branch onto Live and creates a new version in Live's history. It never replaces Live outright, so nobody's work gets silently overwritten.

## The environments

<Tabs>
  <Tab title="Sandbox" icon="flask">
    Sandbox is where every Branch and Sub-branch lives while you work on it.

    **Use a Branch in Sandbox for:**
    - Writing or editing KB topics
    - Adjusting rules and behavior
    - Changing voice settings
    - Wiring or modifying actions, SMS, or handoffs

    <AccordionGroup>
      <Accordion title="Best practices" icon="circle-check">
        - Check the navigation bar so you know which Branch or Sub-branch you are in
        - Test after every meaningful change – your work saves as you go
        - Keep each Branch focused on one piece of work
      </Accordion>

      <Accordion title="Verification" icon="magnifying-glass">
        - In-app chat and call testing reflects your latest changes
        - Nothing in Sandbox can reach a real phone number or API
      </Accordion>
    </AccordionGroup>
  </Tab>

  <Tab title="Staging" icon="vial">
    Staging is **optional**. Use it when in-app testing is not enough.

    **Use Staging for:**
    - Testing with a real phone number
    - Testing against API connections
    - Final voice and pacing checks over a real call

    <AccordionGroup>
      <Accordion title="Best practices" icon="circle-check">
        - Move a Branch into Staging once its in-app tests pass
        - Only one Branch can be in Staging at a time
        - Re-run your key tests over a real call:
          - Simple FAQ (Chat and Call)
          - Voice and greeting
          - Out-of-scope refusal
          - Any topics or actions you've added
      </Accordion>

      <Accordion title="Verification" icon="magnifying-glass">
        - The staging number reaches your Branch, not Live
        - No unexpected KB topics are triggered
        - Behavior matches what you saw in Sandbox
      </Accordion>
    </AccordionGroup>
  </Tab>

  <Tab title="Live" icon="signal-stream">
    Live is **production**. Real users are here.

    **Rules for Live:**
    - Never edit directly – create a Branch instead
    - Always know exactly what version is live
    - Every publish is a version you can roll back to

    <AccordionGroup>
      <Accordion title="Best practices" icon="circle-check">
        - Test a Branch before publishing it
        - Confirm the publish explicitly in the dialog
        - Monitor first calls after publishing

        **Example safe publishing habit:**
        Publish → make one test call → open Conversation Review → confirm behavior → continue monitoring
      </Accordion>
    </AccordionGroup>
  </Tab>
</Tabs>

## Working with others

Two ways to work in parallel:

<CardGroup cols={2}>
  <Card title="Ship together" icon="people-group">
    Share one Branch and give each person a **Sub-branch**. Merge each Sub-branch back as it finishes, test the Branch as a whole, then publish. Everything lands on Live at once.
  </Card>
  <Card title="Ship independently" icon="person-running">
    Each person opens their own Branch and publishes on their own schedule. Branches never merge into each other; each one publishes to Live on its own.
  </Card>
</CardGroup>

Nobody queues behind anyone. While one team spends weeks on a new flow in their Branch, a colleague can open a small Branch, update the knowledge base, and publish the same day.

## Comparing versions

The **Compare versions** view is your primary safety tool.

<CardGroup cols={2}>
  <Card title="What it shows" icon="code-compare">
    - Added KB topics
    - Modified content
    - Removed actions
    - Function wiring changes
    - Sample question edits
  </Card>
  <Card title="When to use it" icon="shield-check">
    Before every publish, to verify all changes are intentional
  </Card>
</CardGroup>

If you can't explain every change in the diff, don't publish.

## Rollbacks

Rollbacks are instant and safe.

<AccordionGroup>
  <Accordion title="When to roll back" icon="clock-rotate-left">
    - A KB topic misfires
    - Voice sounds wrong
    - Handoffs spike unexpectedly
    - A publish introduces confusion
  </Accordion>

  <Accordion title="How to roll back" icon="list-ol">
    1. Open Live's version history – every publish is a version there
    2. Select a known-good version and click rollback
    3. Confirm
    4. Verify with a live test call

    Rollback restores behavior immediately without deleting newer versions, and because publishing merges rather than replaces, nobody else's publish can silently undo it.
  </Accordion>
</AccordionGroup>

## Common mistakes

<Warning>
  **Avoid these pitfalls:**
  - Making a quick change without noticing which Branch you are in
  - Leaving a Branch out of sync and letting conflicts pile up
  - Skipping version comparison before publishing
  - Testing in Sandbox when the behavior depends on a real phone call – use Staging
</Warning>

## Try it yourself

<Steps>
  <Step title="Challenge: pre-publish checklist">
    You've made three changes in your Branch: updated the pet policy topic, added a new SMS offer for late checkout, and changed the agent voice stability from 0.6 to 0.8.

    List **at least 4 specific tests** you would run before publishing.

    <Accordion title="Hint">
      Think about each change you made and what could have broken. Also consider: what tests should always run, regardless of what changed?
    </Accordion>

    <Accordion title="Example solution">
      1. **Test pet policy topic** – ask "are dogs allowed?" in both Chat and Call; confirm the correct topic triggers.
      2. **Test SMS consent flow** – ask "can you text me the late checkout info?" and confirm the agent asks for consent before sending.
      3. **Make a test call from Staging** – listen for the voice stability change over a real call; confirm no audio artifacts were introduced.
      4. **Run a regression test** – test a simple FAQ, out-of-scope refusal, and a handoff to confirm nothing regressed.
      5. **Compare versions** – open the diff and confirm the three changes are the only ones present.
    </Accordion>
  </Step>
</Steps>
