Use Releases to keep work isolated, test it safely, and publish onto Live without disturbing anyone else. This page covers the everyday workflows. For how the model fits together, see [Deployments](/environments-and-versions/introduction).

## Quick reference

| I need to... | Action |
|---|---|
| Start a piece of work | From Live, create a **Release** |
| Split work across people | Create **Branches** from that Release |
| Test with a real phone number | Move the Release to **Staging** |
| Ship it | **Publish** the Release onto Live |
| Catch up with Live | **Sync**, then resolve any conflicts |
| Undo a bad publish | Open Live's version history and **roll back** |
| Compare versions | Select two versions and click **Compare** |

## Publishing

Publishing merges your Release onto Live and creates a new version in Live's history.

<Steps>
  <Step title="Test your Release">
    Run [simulation tests](/testing/simulation-tests), or talk to the agent over an in-app call or chat. Move it to Staging first if you need a real phone number.
  </Step>
  <Step title="Sync if you are out of sync">
    If Live has moved on, sync and resolve any conflicts before you publish.
  </Step>
  <Step title="Publish, and add a description">
    Say what changed and note anything a future collaborator should know.
  </Step>
</Steps>

A published version includes FAQs, Sources configs, functions, agent settings, response controls, routing rules, API integrations, and test sets.

<Tip>Use descriptive version descriptions. For example: "Added Spanish language support with new voice", "Fixed booking function timeout", "Updated holiday hours".</Tip>

<Note>Sources content is synced separately. Sync sources before publishing so the latest content is available.</Note>

## Rolling back

Roll back when a new version has critical bugs, performance degrades, or customer complaints spike.

<Steps>
  <Step title="Open Live's version history">
    Every publish is a version there.
  </Step>
  <Step title="Select the last known good version and roll back">
    Live returns to that version in one step.
  </Step>
</Steps>

**Time to roll back:** 2 to 5 minutes. Afterwards, investigate the issue, fix it in a Release, and publish when ready. Because publishing merges rather than replaces, nobody else's publish can silently undo your rollback.

## Deployment workflows

### Everyday change

1. Create a Release from Live.
2. Make the change and test it.
3. Publish, with a descriptive note.

### Hotfix

1. Create a Release from Live, so you start from exactly what is running.
2. Reproduce the issue, fix it, and test.
3. Publish and monitor closely.

Because the Release branches off Live and merges straight back, no in-progress work rides along with the fix.

### Feature built by several people

1. Create one shared Release for the piece of work.
2. Each person creates a Branch from it and tests their own changes.
3. Merge each Branch back into the Release as it is finished.
4. Test the Release as a whole, then publish.

### Seasonal updates

1. Apply the seasonal changes in a Release, such as hours and policies.
2. Test, then publish for the right date.
3. Revert with a new Release, or roll back, once the season ends.

## Best practices

- **Publish regularly.** Do not accumulate too many changes in one Release.
- **Run [tests](/testing/simulation-tests) before publishing.** Tests run on any Release or Branch, so you catch regressions before anything merges.
- **Sync early.** If your Release is marked out of sync, pull the changes in rather than leaving conflicts to pile up.
- **Monitor after publishing.** Watch the first 30 minutes closely and check metrics for 24 hours.
- **Know your rollback target.** Identify the last good version before you publish.
- **Use consistent descriptions.** Tags such as `[HOTFIX]`, `[FEATURE]` and `[SEASONAL]` make history easy to scan.
