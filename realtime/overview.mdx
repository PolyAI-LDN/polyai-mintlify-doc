Most of the delay callers actually notice isn't the model thinking. It's the system deciding the caller is done talking, then handing a transcript across a stage boundary before generation can even start — comparing model speed alone measures the smallest part of that turn.

<Frame caption="A conventional cascaded pipeline, where each stage waits for the one before it. The largest single cost is deciding the caller has actually stopped talking, not the thinking.">
  <img src="/images/realtime/anatomy-of-one-turn.png" alt="Diagram of a traditional cascaded pipeline turn, showing deciding they're done as the largest segment, followed by smaller hear, think, and speak stages" />
</Frame>

A realtime API has to make that call continuously, holding one open stream of audio and events rather than answering one request at a time: when the caller has finished talking, what happens if they start again mid-answer, and what the agent knows at any given moment.

For the wire format, see the [reference](/realtime/reference). For a runnable example, start with the [quickstart](/realtime/quickstart).

## Why it's built this way

A conventional voice pipeline runs speech recognition, then a language model, then speech synthesis, each stage waiting for the one before it to finish.

<Frame caption="The useful target is the window in which a person would normally reply.">
  <img src="/images/realtime/human-reply-window.png" alt="Chart showing the human reply window of 200-500ms, versus the 1-second mark where a pause starts to read as a dropped call" />
</Frame>

Every stage is a place a turn can go slow, and a place a transcript loses everything about the audio that isn't words: tone, hesitation, the sound of someone still deciding what to say.

Raven Omni collapses the first two stages into one model. It hears the call directly, and the transcript comes out as a byproduct of generating the reply, not a job that has to finish first — more on this in [Generation and transcription](#generation-and-transcription) below.

It also reasons selectively. Most turns don't need a distinct thinking step, so Raven decides per turn whether one is worth the time, and keeps it short when it runs one — see [Automatic reasoning](#automatic-reasoning).

Raven still answers in text, not audio. That's deliberate: it gives you a place to log, test, and run the same guardrails you use elsewhere in the platform before anything is spoken aloud. Pair the streamed reply with your own text-to-speech, the same as you would today.

## The core split

Inside a turn, two mechanisms are doing separate jobs:

<CardGroup cols={2}>
  <Card title="Turn-taking" icon="waveform-lines">
    Deciding *when* a turn ends: that the caller has stopped talking and it's the agent's turn to respond. Server-owned today, via voice activity detection — infrastructure, not where Raven's fusion does its work.
  </Card>
  <Card title="Generation" icon="message-bot">
    Deciding *what* happens once a turn starts: the reply itself, streamed token by token, with transcription and tool calls folded into the same stream.
  </Card>
</CardGroup>

Turn-taking is infrastructure; generation is the model. You don't configure the first one much, and you don't need to. Instructions, tools, and prompting all live in the second.

## What you'll need, by what you're building

| You are building... | Use |
|---|---|
| A phone-style agent with barge-in | Server VAD (`turn_detection: {"type": "server_vad"}`), and let `speech_started`/`speech_stopped` drive turns automatically |
| A push-to-talk or chat-like text UI | Manual turns: `create_response: false`, then `input_audio_buffer.commit` or `conversation.item.create` followed by an explicit `response.create` |
| A tool-using agent | Declare `tools` in `session.update`; answer a call with `function_call_output`, then a fresh `response.create` |
| A task with real thinking to do (dates, ambiguous requests, multi-step logic) | Automatic reasoning is on by default; tune it with `reasoning.effort` in `session.update` |
| Voice output today | Not yet available. Raven answers in text only; pair it with your own text-to-speech |

## How the pieces fit together

### Turn-taking

Turn-taking runs server-side, continuously, over whatever audio you stream in. Voice activity detection makes the call, not the model: `speech_started` opens a turn, `speech_stopped` closes it and commits the turn's audio to history.

It's worth taking seriously even though it's "just" VAD: deciding a caller has finished talking is usually the single largest cost in a turn, ahead of generation. Getting it wrong in either direction, cutting someone off or leaving dead air, is what a caller actually notices.

That placement is deliberate. OpenAI's Realtime API and Gemini's Live API both own turn-taking centrally too, because pushing end-of-speech detection onto every client is a worse default than solving it once.

**Barge-in cancels the in-flight response.** If the caller starts talking again while a response is still streaming, that response is cancelled automatically. The server has no way to know how much of the cancelled reply your text-to-speech had already spoken aloud, so conversation history reflects what Raven sent rather than what the caller heard. Worth accounting for if you're keeping a strict transcript.

### Generation and transcription

This is the fusion described above, as it shows up on the wire: when a turn's last item is audio, Raven transcribes it and answers it in the same completion. The transcript is a by-product of generating the reply, not a separate async job racing it.

A client that assumes the transcript always finishes streaming before the response text starts is assuming something the protocol doesn't promise.

### Automatic reasoning

Most turns don't need a distinct thinking step. A request for store hours doesn't call for the same treatment as "move my Tuesday appointment to whichever Friday is a week after the one after next." Raven decides per turn whether reasoning is worth the time, rather than spending a fixed reasoning budget on every reply regardless of whether it's needed.

`reasoning.effort` in `session.update` influences how much of that budget it's willing to spend. Field-by-field behavior is coming to the [reference](/realtime/reference); for now, the default is tuned to stay fast on simple turns and only slow down when a turn actually calls for it.

### Tool calling

Tool calling is the same **add-then-respond** shape used everywhere else on this API, applied to results instead of messages. A tool call arrives as streamed arguments, the same way text does. You run the tool, add a `function_call_output` item to the conversation, then send a fresh `response.create`.

That last step is the one people miss. A tool result sitting in history doesn't trigger a reply on its own, any more than a user message does.

<Note>
**Text out, by design, not just for now.** `output_modalities` is locked to `["text"]`. Answering in text before a separate voice layer speaks it means the reply can be logged, tested, and run through the same guardrails as everything else on the platform, before a caller ever hears it. Everything else about the protocol, the event vocabulary, the session object, function calling, is shaped so that a future audio-out mode slots in without changing what you've already built. Until then, pair the streamed reply with your own text-to-speech.
</Note>

## Prompting and agent harnesses

`instructions` is a system prompt, sent as-is and forwarded to the model with no rewriting or templating in between. There's no separate persona layer and no prompt-assembly step happening on the server.

That's simpler than a full agent framework, and deliberately so. This API gives you a conversation and a model, and leaves the structure of a business's worth of conversational logic to you. Branching dialogue flows, guardrails, and knowledge bases belong to a harness sitting in front of the protocol.

A harness's job is everything this API doesn't do for you: capturing and encoding audio, deciding what instructions to send and when to update them, running tools and feeding results back, and, until Raven speaks, turning the streamed text into audio the caller actually hears. You can write that yourself or bring one you already use, like [LiveKit](/realtime/guides/livekit) or [Pipecat](/realtime/guides/pipecat). The [Guides](/realtime/guides/introduction) section covers both paths.

## Common mistakes

Both of these are the same mistake: expecting the protocol to do something it explicitly doesn't.

**Requesting audio back returns an error.**

```json wrong: expecting audio back
{
  "type": "session.update",
  "session": { "output_modalities": ["audio"] }
}
```
```json right: text only, for now
{
  "type": "session.update",
  "session": { "output_modalities": ["text"] }
}
```

Asking for `["audio"]` returns an error rather than a silent response, so you find out immediately instead of debugging a mysteriously quiet integration.

**A tool result never answers on its own.**

```json wrong: expecting the tool result alone to answer
{
  "type": "conversation.item.create",
  "item": { "type": "function_call_output", "call_id": "call_abc123", "output": "{...}" }
}
// nothing else sent, and nothing happens
```
```json right: a tool result is followed by a fresh response.create
{
  "type": "conversation.item.create",
  "item": { "type": "function_call_output", "call_id": "call_abc123", "output": "{...}" }
}
{ "type": "response.create" }
```

Adding an item, any item, never implies a reply. That's true of user messages, and just as true of tool results.
