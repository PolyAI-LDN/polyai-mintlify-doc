One WebSocket, held open for as long as you're talking. Here's how the pieces (the connection, the session, and a turn of conversation) fit together, ending in a complete working example.

**Prerequisites:** an API key, a WebSocket-capable client in any language, and five minutes.

## Getting an API key

A Realtime API key comes from the same place as your other PolyAI API credentials: your account dashboard, or your PolyAI contact if you don't have dashboard access yet. It's a single bearer token; there's no separate setup step to enable Realtime specifically, and no OAuth handshake to work through before your first connection.

Treat it like any other bearer credential: store it in an environment variable or secret manager, not in source control, and don't ship it to a browser or device you don't control, more on that in a moment.

## A connection is a conversation

You open one WebSocket and keep it open. There's no per-request auth, no separate call for each turn. The connection itself *is* the conversation, and everything you send or receive travels over it as JSON text frames, using a realtime, event-based protocol.

To open it, connect and pass your API key as a bearer token:

```text connect
URL:     wss://<your-realtime-host>/public_api/v1/realtime
Header:  Authorization: Bearer YOUR_API_KEY
```

<Warning>
**Keep your key server-side.** Treat it like any bearer credential: call it from a server or trusted backend, not from code that ships to a browser or a device you don't control.
</Warning>

The moment the connection is accepted, before you've sent anything at all, the server sends you a `session.created` event. You're already in a session, it just has default settings you probably want to change.

## Telling it how to behave

That default-then-customize pattern is deliberate: connecting always succeeds and always gives you something to talk to, and configuration is a separate step layered on top rather than a pile of required connection parameters. You customize by sending `session.update` (instructions, tools, and so on), and the server replies with `session.updated`, echoing back the full configuration now in effect.

```json you send: session.update
{
  "type": "session.update",
  "session": {
    "instructions": "You are a helpful, concise assistant.",
    "output_modalities": ["text"]
  }
}
```

One field here isn't really optional: `output_modalities` has to be `["text"]`. This API doesn't speak audio back to you yet, so it's worth setting explicitly rather than leaning on a default that could change. A session update is cheap, and you can send another one later if your needs change mid-conversation.

## The shape of a turn

Once configured, talking to Raven is always the same two-part move, and it's worth understanding why it's two parts rather than one. **Adding** something to the conversation and **asking for a response** to it are separate events:

```json you send: conversation.item.create
{
  "type": "conversation.item.create",
  "item": {
    "type": "message",
    "role": "user",
    "content": [{ "type": "input_text", "text": "What's the capital of France?" }]
  }
}
```

```json you send: response.create
{ "type": "response.create" }
```

That separation is what makes a few useful things possible later: you can seed a conversation with prior history without triggering a reply to each item, and, once you're using tools, you can add a tool's result to the conversation and ask for the follow-up in a second step, since a tool result on its own doesn't end a turn.

For now, the two always travel together: add the message, then ask for a response to it.

## Watching the answer arrive

The reply comes back as a short burst of events rather than one block of JSON. It's a stream, and streams are made of small pieces arriving in order. Most of them you can ignore at first; the two that matter are `response.output_text.delta`, which you append piece by piece to build the reply as it's typed out, and `response.done`, which tells you the turn is over and how it ended.

```text server sends: the response
response.created
response.output_item.added
response.content_part.added
response.output_text.delta   delta: "The"
response.output_text.delta   delta: " capital"
response.output_text.delta   delta: " of France is Paris."
response.output_text.done
response.content_part.done
response.output_item.done
response.done                response.status: "completed"
```

> **raven-omni-api-preview:** "The capital of France is Paris."

Everything between `response.created` and `response.done` is bookkeeping that a fuller integration will eventually care about: which output item is being written, where its one content part begins and ends. For a first pass, the deltas and the final status are enough to hold a conversation.

And that's the whole loop: add an item, ask for a response, collect the deltas until `response.done`. A longer conversation is just this, repeated. Each new message builds on everything already in the conversation, with nothing else to track on your end.

## All of it, together

The same sequence as one script: no special SDK, no realtime-specific library, just the standard `websockets` package. Locally, that means Python 3.10 or later, `pip install websockets`, and `RAVEN_API_KEY` set in your shell, nothing else to install or stand up.

```python python
# pip install websockets
import asyncio, json, os, websockets

URL = "wss://<your-realtime-host>/public_api/v1/realtime"
API_KEY = os.environ["RAVEN_API_KEY"]

async def main():
    headers = {"Authorization": f"Bearer {API_KEY}"}
    async with websockets.connect(URL, additional_headers=headers) as ws:
        await ws.recv()  # session.created

        await ws.send(json.dumps({
            "type": "session.update",
            "session": {"instructions": "Be concise.", "output_modalities": ["text"]},
        }))
        await ws.recv()  # session.updated

        await ws.send(json.dumps({
            "type": "conversation.item.create",
            "item": {
                "type": "message", "role": "user",
                "content": [{"type": "input_text", "text": "What's the capital of France?"}],
            },
        }))
        await ws.send(json.dumps({"type": "response.create"}))

        reply = ""
        async for raw in ws:
            event = json.loads(raw)
            if event["type"] == "response.output_text.delta":
                reply += event["delta"]
            elif event["type"] == "response.done":
                print(reply)
                break

asyncio.run(main())
```

## Beyond a single turn

The same add-then-respond shape extends naturally in a couple of directions:

- **Function calling**: declare tools in `session.tools`; a call arrives as `response.function_call_arguments.done`, and you answer it with a `function_call_output` item, followed by another `response.create`, the same two-part pattern from earlier, just with a tool result instead of a user message.
- **Voice in**: append PCM16 audio via `input_audio_buffer.append` instead of creating a text item; Raven transcribes speech as part of the same response, streaming the transcript alongside the reply.
