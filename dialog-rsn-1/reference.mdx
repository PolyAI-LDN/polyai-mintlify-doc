The Realtime API holds one conversation over one WebSocket connection, for as long as the client stays connected. It's a realtime, event-based protocol: JSON text frames, a persistent session object, streamed responses. An existing realtime client works with few changes.

This page explains how the pieces behave together. The [Dialog-RSN-1 API reference](/api-reference/dialog-rsn-1/reference) is the contract: hosts and authentication, every session field, every event, PolyAI extensions, error and close codes. [Limits and pricing](/api-reference/dialog-rsn-1/limits) has the numbers. New to this API? Start with the [quickstart](/dialog-rsn-1/quickstart).

## Connecting

Open `wss://api.studio.poly.ai/v1/realtime` with your API key in an `X-API-KEY` or `Authorization: Bearer` header. On connect, the server sends `session.created` with the default session. You don't need to send anything to open the conversation.

This is plain JSON over a plain WebSocket, so any WebSocket client in any language can speak it. No SDK is needed.

<Warning>
**Keep your key server-side.** A native browser `WebSocket` can't set headers, so it can't authenticate directly. Put a relay on your own server that holds the key and opens the upstream connection, as the [browser guide](/dialog-rsn-1/guides/javascript-browser#connecting-from-the-browser) does.
</Warning>

Regional hosts, which key works on which host, and what each refused handshake returns are in [Connect](/api-reference/dialog-rsn-1/reference#connect) and [Authenticate](/api-reference/dialog-rsn-1/reference#authenticate).

## The session object

Send `session.update` to configure the conversation; `session.created` and `session.updated` echo the effective session back. A partial update deep-merges onto the current session, so updating `instructions` doesn't wipe `tools`.

An update is applied whole or not at all. One field the service refuses, and nothing in that update takes effect: you get an `error` naming the field and no `session.updated`. So what `session.updated` echoes is exactly what's in effect.

```json session.update
{
  "type": "session.update",
  "session": {
    "type": "realtime",
    "instructions": "You are a helpful voice assistant. Keep responses brief.",
    "audio": {
      "input": {
        "format": { "type": "audio/pcm" },
        "turn_detection": { "type": "server_vad", "create_response": true }
      }
    }
  }
}
```

Which fields are honoured, which are accepted and ignored, and which are refused: [Configure the session](/api-reference/dialog-rsn-1/reference#configure-the-session). The `poly_` fields, such as `poly_knowledge` and `poly_response_language`, are in [PolyAI extensions](/api-reference/dialog-rsn-1/reference#polyai-extensions).

## Turn-taking and audio

Voice activity detection proposes a boundary, and Dialog-RSN-1 confirms the end of every turn before `speech_stopped` reaches you.

Detection runs in-process over every appended frame. Crossing into speech opens a turn and mints its item id up front, since `speech_started` has to name an item before the audio finishes arriving.

Crossing back out of speech doesn't commit the turn by itself: it triggers a turn-status check, folded into the same generation that becomes the reply if Dialog-RSN-1 confirms the caller is done. If Dialog-RSN-1 says the turn is still ongoing, the buffer keeps growing and the check re-runs on a timer, capped after a few seconds, rather than sending anything to you.

`speech_stopped` reports that confirmed judgment, never the detector's raw signal, so a mid-sentence pause that the detector reads as silence doesn't surface as a turn boundary if Dialog-RSN-1 says the caller isn't finished. `speech_started` is the detector's own signal while nothing is playing, and is confirmed by the model first only while a reply is audible. A turn the model then judges to be noise is dropped, so a `speech_started` can arrive with no `speech_stopped` after it.

Setting `turn_detection.create_response: false` skips the confirmation. Turns are taken at face value: the turn commits at the first pause the detector hears, or when you send `input_audio_buffer.commit`, and nothing answers it until an explicit `response.create`. A pause long enough for the detector splits the caller's speech into two items in history.

Setting `turn_detection: null` turns detection off, for push-to-talk. The detector and the model's turn check don't run. Everything you append, silence included, is one turn until you send `input_audio_buffer.commit`, and only `response.create` starts a reply. No `speech_started` or `speech_stopped` is sent, only `input_audio_buffer.committed`. Nothing barges in, so send `response.cancel` to stop a reply. Send a `turn_detection` object to turn detection back on.

<Warning>
**Turn timing is not tunable.** `create_response` is the only part of `turn_detection` this service reads. The timing fields are accepted and ignored, and two fields are refused: see [Configure the session](/api-reference/dialog-rsn-1/reference#configure-the-session).
</Warning>

The detector's thresholds are fixed at build time. Tune turn-taking behavior in [`instructions`](/dialog-rsn-1/prompt-guide#turn-taking) instead, which is where this service puts that decision.

**Barge-in cancels the in-flight response.** If the caller starts talking again while a response is still streaming, Dialog-RSN-1 confirms it's the caller before cancelling that response (the same as if the client had sent `response.cancel`), and the usual `response.done(status: "cancelled")` follows. There's no separate signal for this; watch for `response.done` with a cancelled status arriving unprompted, right after a `speech_started` you didn't ask for.

That confirmation runs for as long as the reply is audible, and the server's idea of "audible" is only as good as what you tell it. On its own it's an estimate: how long the reply takes to say at a typical speaking rate. If your text-to-speech runs slower or starts late, sound arriving after the estimate ends is forwarded without confirmation. Sending [playback reports](#playback-reports) replaces the estimate with your real playback, so a backchannel two seconds into a spoken reply gets checked like any other interruption. When the server speaks the reply, it knows where playback is and needs no reports.

## Voice input and transcription

Dialog-RSN-1 transcribes spoken audio as part of the same generation that answers the turn. When a turn's last item is user audio, the model both answers the turn and produces its transcript in one completion, streamed to the client as `conversation.item.input_audio_transcription.delta`/`.completed`, attributed back to the audio item's id.

<Note>
**A timing note.** The transcript is a by-product of the same generation that answers the turn, not an independent asynchronous pass. Don't rely on the transcript arriving before the response text starts.
</Note>

## Text or spoken replies

A new session speaks its replies. Dialog-RSN-1 writes each reply and the server voices it, so you choose whether to take the speech or the text.

- **`output_modalities: ["audio"]`**: the default. The server speaks the reply. The sound streams as `response.output_audio.delta`, base64 PCM16 mono at 24 kHz, sent at the pace it plays. The words stream as `response.output_audio_transcript.delta`. Pick the voice with `audio.output.voice`, a Cartesia voice id; leave it unset for the default voice. `response.done` arrives once the reply has finished playing.
- **`output_modalities: ["text"]`**: bring your own text-to-speech. The reply streams as `response.output_text.delta`, with no audio events, and you speak it however you like. Use it when you want your own voice or vendor, control over playback, or a place to log the reply and run your guardrails before a caller hears it. Then send [playback reports](#playback-reports), so barge-in and history follow what the caller really heard.

A speaking session sends no `response.output_text.delta`, so a client that reads only text deltas sees an empty reply and no error. Read the transcript deltas, or set `["text"]`. Asking for both modalities at once is refused with `invalid_request_error`.

## Function calling

Tool calls stream the same way text does: incremental arguments, then a `.done` naming the call.

Declare tools in `session.tools`. When the model calls one, arguments stream via `response.function_call_arguments.delta`, closing with `.done` carrying `name`, full `arguments`, and a server-minted `call_id`. Answer it with `conversation.item.create` (`type: "function_call_output"`, matching `call_id`), then a fresh `response.create`. A tool result carries no audio, so nothing else would trigger the follow-up turn.

<Warning>
**A mismatched `call_id` is never refused.** A `function_call_output` whose `call_id` doesn't match the outstanding call is accepted and kept as an item you can retrieve, but it's left out of what the model sees. The model then answers as if the tool never returned. Echo the `call_id` from `response.function_call_arguments.done` exactly.
</Warning>

Example, for a tool declared as `get_weather(location: string)`:

```json round trip
// model calls the tool
{ "type": "response.function_call_arguments.done",
  "name": "get_weather", "arguments": "{\"location\": \"Tokyo\"}",
  "call_id": "call_f02ca25a548c4a6ea8c5d8f8e89d25d6" }

// client answers with a mocked result
{ "type": "conversation.item.create",
  "item": { "type": "function_call_output",
             "call_id": "call_f02ca25a548c4a6ea8c5d8f8e89d25d6",
             "output": "{\"location\": \"Tokyo\", \"temperature_f\": 68, \"condition\": \"partly cloudy\"}" } }

// model's final reply, next response.create
"It's 68 degrees and partly cloudy in Tokyo."
```

To have the model say something to the caller while a slow tool runs, mark one string parameter with `poly_spoken`. See [PolyAI extensions](/api-reference/dialog-rsn-1/reference#polyai-extensions) and the [prompt guide](/dialog-rsn-1/prompt-guide).

## Playback reports

When you bring your own text-to-speech, only you know what the caller has heard. OpenAI's server owns audio output, so its protocol has no events for this. Dialog-RSN-1 adds three, namespaced `poly.` the way field extensions are namespaced `poly_`: `poly.output_audio.started`, `.delta` and `.stopped`.

Sending them makes the barge-in confirmation window follow your real playback. See [Turn-taking and audio](#turn-taking-and-audio). They also set history: after `poly.output_audio.stopped`, the reply is kept as `spoken_text`, ending in a dash if `dropped_ms` says it was cut off. Each report applies to the response it names, so carry the `response_id` from `response.created` through every report about it.

The event shapes and how often to send them are in [PolyAI extensions](/api-reference/dialog-rsn-1/reference#polyai-extensions).

<Note>
**Optional.** A client that sends none of these gets an estimate instead: the server treats a reply as audible for as long as it takes to say at a typical speaking rate, and after a barge-in keeps the words it estimates were heard. The first report you send replaces the estimate for the rest of the session. On a reply the server speaks itself, it tracks playback and ignores these reports.
</Note>

## Errors

Almost every failure answers with an `error` event and keeps the connection open. One malformed frame has not earned a disconnect. A few close the socket, such as an oversized frame or a session that fails to start. Branch on `error.code`, never on the message.

Every code, whether to retry, and every close code are in [Errors](/api-reference/dialog-rsn-1/reference#errors).

## Known limitations

These are deliberate scope cuts.

- **Truncation of a text reply is acknowledged, not applied.** On a reply you voice yourself, `conversation.item.truncate` validates the item and replies, but leaves history untouched: mapping a millisecond offset onto a character offset needs TTS timing the protocol has nowhere to carry. Send [playback reports](#playback-reports) instead, which set history to the words heard.
- **Without playback reports, barge-in timing and history are estimates.** The server estimates how long a reply is audible from a typical speaking rate, and after a barge-in keeps the words it estimates were heard. If your text-to-speech runs behind that estimate, sound arriving after it ends is forwarded as an interruption without confirmation. [Playback reports](#playback-reports) close the gap.
- **No MCP tools.** Only function tool entries are honored; an MCP tool declaration is rejected with `unsupported_parameter`.
- **Turn timing isn't configurable.** Only `create_response` is read. See [Turn-taking and audio](#turn-taking-and-audio).
- **Transcription usage is a duration, not a token count.** `conversation.item.input_audio_transcription.completed` reports audio duration. Response token counts are separate, and do arrive on `response.usage`.
- **History is bounded.** From the tenth caller audio turn, older turns release their audio and keep their transcript. Where older history is summarised or dropped to fit the context window, the first `response.done` after that lists the items the prompt now leaves out in `poly_compacted_item_ids`; the items stay in history. A conversation that still outgrows the window fails that response with `context_length_exceeded`; the connection stays open.
- **One response in flight per connection.** A `response.create` while a response is open is refused with `conversation_already_has_active_response`. A confirmed barge-in cancels the open response.
- **No session resumption.** A dropped connection has no resumption handle to pick back up with, unlike OpenAI's or Gemini's resumption tokens. Reconnect and resend whatever context the new session needs.

## Example flows

Three complete conversations, shown as `dialog-rsn-1` returns them. Flow 1 uses the default spoken output; flows 2 and 3 set `output_modalities: ["text"]`, so the reply arrives as `output_text.delta`.

### 1. A plain question, driven manually

Session configured with `create_response: false`, so nothing answers until asked.

1. **Client → server:** `conversation.item.create`, a real user message: *"What's the capital of France? Answer in one short sentence."*
2. **Server → client:** `conversation.item.added` → `.done`
3. **Client → server:** `response.create`
4. **Server → client:** `response.created` → `output_item.added` → `content_part.added` → `output_audio_transcript.delta` ×N → `output_audio.delta` ×N → `output_audio.done` → `output_audio_transcript.done` → `content_part.done` → `output_item.done` → `response.done`

> **dialog-rsn-1:** "The capital of France is Paris."

### 2. Tool calling, end to end

1. **Client → server:** `session.update` with `tools: [get_time, get_weather]`
2. **Client → server:** `response.create`, off "What time is it right now?"
3. **Server → client:** `response.function_call_arguments.done`, `get_time({})` → `call_000a14b52c2c4c9dae5a307369fad224`
4. **Client → server:** `conversation.item.create` (`function_call_output`, mocked result `{"time": "11:04 AM", "timezone": "CDT"}`) + `response.create`
5. **Server → client:** `response.output_text.delta` → `response.done`

> **dialog-rsn-1:** "It's 11:04 AM."

### 3. Cancellation mid-stream

1. **Client → server:** `response.create`
2. **Server → client:** `response.created` → a few `output_text.delta`
3. **Client → server:** `response.cancel`
4. **Server → client:** `response.done`, status `"cancelled"`. Any open output item closes as `incomplete`, so a client waiting on a matching `.done` isn't left hanging.
