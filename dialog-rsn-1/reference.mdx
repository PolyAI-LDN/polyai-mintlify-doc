The Realtime API holds one conversation over one WebSocket connection, for as long as the client stays connected. It's a realtime, event-based protocol: JSON text frames, a persistent session object, streamed responses. An existing realtime client works with few changes.

Start with the [quickstart](/dialog-rsn-1/quickstart) for a walkthrough of how the pieces fit together, ending in a complete working example.

For hosts, the accepted `session.update` fields, error and close codes, and limits, see the [Dialog-RSN-1 API reference](/api-reference/dialog-rsn-1/reference) and [limits and pricing](/api-reference/dialog-rsn-1/limits).

## Connecting

<CodeGroup>

```text websocket
wss://api.studio.poly.ai/v1/realtime
X-API-KEY: YOUR_API_KEY
```

</CodeGroup>

On connect, the server sends `session.created` with the effective (default) session. You don't need to send anything to open the conversation.

<Warning>
**`X-API-KEY` or `Authorization: Bearer`.** Send the key in either header. A WebSocket subprotocol credential isn't accepted, so a native browser `WebSocket` (which can't set headers at all) can't authenticate against this endpoint directly. Put a relay on your own server that holds the key and opens the upstream connection, as the [browser guide](/dialog-rsn-1/guides/javascript-browser#connecting-from-the-browser) does.

A missing or refused key fails the handshake with `401`. Through the API gateway that answer comes from the gateway itself, which validates the key before the request reaches this service, so the body is the gateway's rather than this API's error shape:

```json
{ "message": "No API key found in request", "request_id": "4076..." }
```

Past the gateway, the service resolves the key again to an account. A key it refuses is another `401`; if the authentication service can't be reached at all you get `503`, which is worth retrying rather than treating as a bad key. On a server without the `websocket.http.response` extension those arrive as close codes `4401` and `4503` instead.
</Warning>

<Note>
**No SDK required.** This is plain JSON over a plain WebSocket. Any WebSocket client in any language can speak this protocol, no special SDK or realtime-specific library needed.
</Note>

<Warning>
**Keep your key server-side.** Treat it like any API credential: call it from a server or trusted backend, not from code that ships to a browser or a device you don't control.
</Warning>

## The session object

Sent inside `session.update`, echoed back on `session.created` / `session.updated`. A partial update deep-merges onto the current session: updating `instructions` does not wipe `tools`.

| Field | Notes |
|---|---|
| `type` | Always `"realtime"`. Omit it and the server fills it in for you. |
| `model` | Informational: setting it, on update or in the connection URL's `?model=`, selects nothing. The service runs Dialog-RSN-1 whatever you pass, and currently echoes `dialog-rsn-1` on `session.created` / `session.updated`. Don't assert on it. |
| `instructions` | System prompt, forwarded as-is. |
| `tools` | Function tools only: `{type, name, description, parameters}`. MCP-server entries are dropped before generation rather than half-supported, and so is a function entry with no `name`. Both are still echoed back in `session.updated`, so the echo is not confirmation that a tool reached the model. |
| `output_modalities` | Must be exactly `["text"]`. The server refuses anything else with an error rather than answering in text, see [Text output only](#text-output-only). |
| `audio.input.format` | `{"type": "audio/pcm"}`. Omit `rate` entirely to get Dialog-RSN-1's native 16 kHz. |
| `audio.input.turn_detection` | `{"type": "server_vad", "create_response": bool}`. **`create_response` is the only field read.** The schema's other turn-detection fields, and `"type": "semantic_vad"`, are rejected with `unsupported_parameter`. See [Turn-taking & audio](#turn-taking-and-audio). |
| `reasoning` | Rejected with `unsupported_parameter`. Reasoning on this service is automatic and per-turn, with no client-side knob. |
| `audio.input.noise_reduction`, `audio.output` | Rejected with `unsupported_parameter`. No noise reduction runs here, and there's no audio output. |
| `poly_knowledge` | *Extension.* Retrieved topics (`[{name, content, actions}]`), the one input Dialog-RSN-1 has with no realtime equivalent. On the session it's a fixed brief, present from the first turn; the same field also rides on a `function_call_output` item, which is what a knowledge base search looks like in practice. Both render into one numbered list the model cites into. |
| `poly_input_rate` | *Extension.* A real client sample rate outside the standard 24 kHz. The server resamples on the way in rather than rejecting it. |

```json session.update
{
  "type": "session.update",
  "session": {
    "type": "realtime",
    "model": "dialog-rsn-1",
    "instructions": "You are a helpful voice assistant. Keep responses brief.",
    "output_modalities": ["text"],
    "audio": {
      "input": {
        "format": { "type": "audio/pcm" },
        "turn_detection": { "type": "server_vad", "create_response": true }
      }
    }
  }
}
```

## Client → server events

The server recognizes all eleven GA client event types, plus the three [playback reports](#playback-reports) below. Two of the GA eleven behave differently because there's no audio output on this API: `conversation.item.truncate` is acknowledged but has no effect, since there's no audio to truncate against, and `output_audio_buffer.clear` returns `invalid_request_error`, since there's no audio output buffer to clear.

| Event | Behavior |
|---|---|
| `session.update` | Deep-merges onto the session. Replies `session.updated`. |
| `input_audio_buffer.append` | Base64 PCM16 audio. Fed to voice-activity detection frame-by-frame; may trigger `speech_started`/`speech_stopped`. |
| `input_audio_buffer.commit` | Ends the current turn manually, same path detection uses on `speech_stopped`. For a client driving its own turn-taking. |
| `input_audio_buffer.clear` | Drops buffered, uncommitted audio. Replies `input_audio_buffer.cleared`. |
| `conversation.item.create` | Adds an item to history: a real user/assistant/system message, or a `function_call_output`. Replies `conversation.item.added` then `.done`. |
| `conversation.item.retrieve` | Replies `conversation.item.retrieved`, or `item_not_found`. |
| `conversation.item.delete` | Removes an item. Replies `conversation.item.deleted`. |
| `conversation.item.truncate` | Validated and acknowledged (`conversation.item.truncated`), but history is **not shortened**, see [Known limitations](#known-limitations). |
| `response.create` | Starts a generation over the conversation as it stands. The only way to answer a tool result, since a tool output ends no turn on its own. |
| `response.cancel` | Cancels an in-flight generation. Silent no-op if nothing is running (no error). |
| `output_audio_buffer.clear` | Always answered with `invalid_request_error`, since there's no audio output buffer to clear, over any transport. |

### Playback reports

*Extension.* Three events with no GA equivalent, because there is nothing to be equivalent to: OpenAI's server owns audio output and already knows what a caller is hearing. Here you own the text-to-speech, so only you know. Event extensions are namespaced `poly.`, the way field extensions are namespaced `poly_`.

| Event | Behavior |
|---|---|
| `poly.output_audio.started` | The caller has begun hearing `response_id`. |
| `poly.output_audio.delta` | Progress while they're still hearing it: `audio_ms` (cumulative, not incremental) and `delta`, the increment of spoken text. |
| `poly.output_audio.stopped` | Playback ended, by finishing or by being cut short: `audio_ms`, `dropped_ms` (synthesized but never played), and `spoken_text`, your synthesizer's account of what was heard. |

Sending these extends the barge-in confirmation window across playback, not just generation. See [Turn-taking & audio](#turn-taking-and-audio). A report naming a response that isn't the one playing is ignored rather than applied to the current one, so carry the `response_id` from `response.created` through every report about it.

<Note>
**Optional, and inert if you skip them.** A client that sends none of these behaves exactly as it did before they existed: the reply is assumed audible the moment it's sent, and assumed heard in full.
</Note>

## Server → client events

Every event this service can send.

**Session**

| Event | Description |
|---|---|
| `session.created` | First event on every connection. |
| `session.updated` | Echoes the full effective session after a merge. |

**Conversation items**

| Event | Description |
|---|---|
| `conversation.item.added` | An item entered history (pre-completion state). |
| `conversation.item.done` | The same item, finalized. Sent whether the *server* or the *client* put the item there. |
| `conversation.item.retrieved` | Answer to `conversation.item.retrieve`. |
| `conversation.item.deleted` | Answer to `conversation.item.delete`. |
| `conversation.item.truncated` | Acknowledges truncation without applying it. |

**Audio input / voice activity detection**

| Event | Description |
|---|---|
| `input_audio_buffer.speech_started` | Detection crossed into speech. Names the item id the turn will become. |
| `input_audio_buffer.speech_stopped` | Detection crossed out of speech; triggers the turn commit. |
| `input_audio_buffer.committed` | The turn's audio joined history as one item. |
| `input_audio_buffer.cleared` | Answer to `input_audio_buffer.clear`. |

**Transcription**

| Event | Description |
|---|---|
| `conversation.item.input_audio_transcription.delta` | Streamed as part of the same generation that answers the turn, not a separate async pass. See [Voice input & transcription](#voice-input-and-transcription). |
| `conversation.item.input_audio_transcription.completed` | Final transcript, plus a duration-based usage figure (no token counting yet). |

**Response lifecycle**

| Event | Description |
|---|---|
| `response.created` | Opens the response; the only place the client learns `response_id`. |
| `response.output_item.added` | An output item (text message or function call) begins. |
| `response.content_part.added` | Text items only: one content part per item, always. |
| `response.output_text.delta` | Incremental text, diffed server-side from whole-snapshot chunks. |
| `response.output_text.done` | Final text for the item. |
| `response.function_call_arguments.delta` | Incremental tool-call arguments. |
| `response.function_call_arguments.done` | Final `name` + `arguments`, plus the `call_id` a reply must echo. |
| `response.content_part.done` | Closes the item's one content part. |
| `response.output_item.done` | Closes the output item. |
| `response.done` | Always terminal, whatever the outcome. Status lives at `response.status` (`completed` / `cancelled` / `failed`). `response.usage` carries `input_tokens`, `output_tokens` and `total_tokens`, and is **absent rather than zeroed** when nothing was counted, so a client reading it must handle its absence. The response also carries two extensions: `poly_cited_topics`, the names of the `poly_knowledge` topics the model answered from, absent rather than empty when it cited nothing; and `poly_out_of_domain`, whether Dialog-RSN-1 judged the request outside what it's deployed to handle, reported on every turn it judges, tool calls included, where `false` is an answer rather than an absence. |

**Errors**

| Event | Description |
|---|---|
| `error` | See [Errors](#errors) for the code taxonomy. |

## Turn-taking and audio

Voice activity detection proposes a boundary; Dialog-RSN-1 confirms it before either event reaches you.

Detection runs in-process over every appended frame. Crossing into speech opens a turn and mints its item id up front, since `speech_started` has to name an item before the audio finishes arriving.

Crossing back out of speech doesn't commit the turn by itself: it triggers a turn-status check, folded into the same generation that becomes the reply if Dialog-RSN-1 confirms the caller is done. If Dialog-RSN-1 says the turn is still ongoing, the buffer keeps growing and the check re-runs on a timer, capped after a few seconds, rather than sending anything to you.

`speech_started` and `speech_stopped` report that confirmed judgment, never the detector's raw signal, so a mid-sentence pause that the detector reads as silence doesn't surface as a turn boundary if Dialog-RSN-1 says the caller isn't finished.

Setting `turn_detection.create_response: false` doesn't change any of that: the audio still joins history once confirmed, but nothing answers it until an explicit `response.create`.

<Warning>
**Turn timing is not tunable.** `create_response` is the only part of `turn_detection` this service reads. `silence_duration_ms`, `prefix_padding_ms`, `threshold`, `idle_timeout_ms`, `interrupt_response` and `"type": "semantic_vad"` are rejected with `unsupported_parameter`, and the rest of that `session.update` is discarded with them.
</Warning>

The detector's thresholds are fixed at build time. Tune turn-taking behavior in [`instructions`](/dialog-rsn-1/prompt-guide#turn-taking) 
instead, which is where this service puts that decision.

**Barge-in cancels the in-flight response.** If the caller starts talking again while a response is still streaming, Dialog-RSN-1 confirms it's the caller before cancelling that response (the same as if the client had sent `response.cancel`), and the usual `response.done(status: "cancelled")` follows. There's no separate signal for this; watch for `response.done` with a cancelled status arriving unprompted, right after a `speech_started` you didn't ask for.

That confirmation runs for as long as the reply is audible, and the server's idea of "audible" is only as good as what you tell it. On its own it can mean nothing more than "still generating", which is a few hundred milliseconds; sound arriving after that, while your text-to-speech is still speaking, is forwarded without confirmation. Sending [playback reports](#playback-reports) extends the window across playback, so a backchannel two seconds into a spoken reply gets checked like any other interruption. See [Known limitations](#known-limitations) for what neither approach solves.

## Voice input and transcription

Dialog-RSN-1 transcribes spoken audio as part of the same generation that answers the turn. When a turn's last item is user audio, the model both answers the turn and produces its transcript in one completion, streamed to the client as `conversation.item.input_audio_transcription.delta`/`.completed`, attributed back to the audio item's id.

<Note>
**A timing note.** The transcript is a by-product of the same generation that answers the turn, not an independent asynchronous pass. Don't rely on the transcript arriving before the response text starts.
</Note>

## Text output only

Dialog-RSN-1 is a text-out model. It hears audio and answers in text, and the spoken half of the call stays yours: pair the streamed reply with your own text-to-speech.

`output_modalities` is fixed to `["text"]` for that reason, and the server refuses a request for `["audio"]` with an error rather than answering in text. There's no `response.output_audio.*` event to listen for and no audio output buffer, which is why `output_audio_buffer.clear` answers `invalid_request_error` and `conversation.item.truncate` has nothing to truncate against.

## Function calling

Tool calls stream the same way text does: incremental arguments, then a `.done` naming the call.

Declare tools in `session.tools`. When the model calls one, arguments stream via `response.function_call_arguments.delta`, closing with `.done` carrying `name`, full `arguments`, and a server-minted `call_id`. Answer it with `conversation.item.create` (`type: "function_call_output"`, matching `call_id`), then a fresh `response.create`. A tool result carries no audio, so nothing else would trigger the follow-up turn.

<Warning>
**A stale `call_id` is rejected only while a call is pending.** If a *different* tool call is outstanding, a `function_call_output` whose `call_id` doesn't match it gets `invalid_request_error` instead of silent acceptance. With nothing pending there's nothing to correlate against, so the item is accepted and enters history as normal. Don't rely on this to catch a mismatched id after the fact.
</Warning>

Example, for a tool declared as `get_weather(location: string)`:

```json round trip
// model calls the tool
{ "type": "response.function_call_arguments.done",
  "name": "get_weather", "arguments": "{\"location\": \"Tokyo\"}",
  "call_id": "call_f02ca25a548c4a6ea8c5d8f8e89d25d6" }

// client answers with a mocked result
{ "type": "conversation.item.create",
  "item": { "type": "function_call_output",
             "call_id": "call_f02ca25a548c4a6ea8c5d8f8e89d25d6",
             "output": "{\"location\": \"Tokyo\", \"temperature_f\": 68, \"condition\": \"partly cloudy\"}" } }

// model's final reply, next response.create
"It's 68 degrees and partly cloudy in Tokyo."
```

## Errors

Every failure mode answers with an `error` event and keeps the connection open. One malformed frame has not earned a disconnect.

| Code | When |
|---|---|
| `unsupported_event_type` | A syntactically valid frame whose `type` is outside the eleven GA client events and the three [playback reports](#playback-reports). |
| `unknown_parameter` | A `session.update` carrying a field that is neither in the schema nor namespaced `poly_`, at any depth. `param` names the full path, e.g. `session.audio.input.transcrption`. **No part of the update is applied** and no `session.updated` follows, so a good field sent alongside a bad one does not take effect either. Real realtime fields this service doesn't support fail with `unsupported_parameter` instead. |
| `unsupported_parameter` | A `session.update` carrying a real realtime field this service doesn't act on: `audio.output`, `audio.input.noise_reduction`, `reasoning`, or any `turn_detection` field but `create_response`. The message says why. As with `unknown_parameter`, **no part of the update is applied**. |
| `invalid_request_error` | Malformed payload of a known type; a stale/mismatched `function_call_output.call_id`; `output_audio_buffer.clear`. |
| `item_not_found` | `conversation.item.retrieve` / `.delete` / `.truncate` against an id that isn't in history. |
| `unsupported_item_type` | A `conversation.item.create` for an item shape this service has no representation for (an MCP call, say), refused rather than silently dropped. |
| `server_error` | The session itself failed to start (no model, no voice-detection weights): the socket accepts, gets one `error`, and closes with code 1011. |
| `generation_failed` | A backend failure mid-generation. Terminates the response with `response.done(status: "failed")` right behind it. The real failure detail stays in server logs, never on the wire. |

## Known limitations

These are deliberate scope cuts.

- **Truncation is acknowledged, not applied.** `conversation.item.truncate` validates the item and replies, but leaves history untouched. Truncation is defined against played audio; this service produces text, and mapping a millisecond offset onto a character offset needs TTS timing the protocol has nowhere to carry.
- **Backchannels interrupt during playback unless you report it.** Dialog-RSN-1's barge-in check runs while a reply is audible, and by default that means only while it's generating. Once generation finishes and your own text-to-speech is still playing it aloud, the server has no way to know, so it forwards any sound in that window as an interruption without confirmation. [Playback reports](#playback-reports) close the window; a client that doesn't send them keeps this behavior.
- **No MCP tools.** Only function tool entries are honored; MCP-server tool declarations are dropped.
- **Turn timing isn't configurable.** The detector's thresholds are fixed, and `silence_duration_ms`, `prefix_padding_ms`, `threshold`, `idle_timeout_ms`, `interrupt_response` and `"type": "semantic_vad"` are rejected with `unsupported_parameter`. Only `create_response` is read. See [Turn-taking & audio](#turn-taking-and-audio).
- **Transcription usage is a duration, not a token count.** `conversation.item.input_audio_transcription.completed` reports audio duration. Response token counts are separate, and do arrive on `response.usage`.
- **No history compaction.** Nothing trims a conversation as it grows, so a long enough call eventually overruns the model's context window.
- **One response in flight per connection.** A new `response.create` (or the caller starting to speak again) cancels whatever was still generating, since two concurrent generations would otherwise interleave onto one socket.
- **Conversation history is what was sent, not what was heard.** Cancelling on barge-in stops generation, but history still holds the whole reply rather than the part your text-to-speech reached before the caller talked over it. `poly.output_audio.stopped` carries `spoken_text` and `dropped_ms` so your side has that account, and the server uses playback reports to judge the interruption, but it does not rewrite history from them. Keep your own record if you're building a strict transcript.
- **No session resumption.** A dropped connection has no resumption handle to pick back up with, unlike OpenAI's or Gemini's resumption tokens. Reconnect and resend whatever context the new session needs.

## Example flows

Three complete conversations, shown as `dialog-rsn-1` returns them.

### 1. A plain question, driven manually

Session configured with `create_response: false`, so nothing answers until asked.

1. **Client → server:** `conversation.item.create`, a real user message: *"What's the capital of France? Answer in one short sentence."*
2. **Server → client:** `conversation.item.added` → `.done`
3. **Client → server:** `response.create`
4. **Server → client:** `response.created` → `output_item.added` → `content_part.added` → `output_text.delta` ×N → `output_text.done` → `content_part.done` → `output_item.done` → `response.done`

> **dialog-rsn-1:** "The capital of France is Paris."

### 2. Tool calling, end to end

1. **Client → server:** `session.update` with `tools: [get_time, get_weather]`
2. **Client → server:** `response.create`, off "What time is it right now?"
3. **Server → client:** `response.function_call_arguments.done`, `get_time({})` → `call_000a14b52c2c4c9dae5a307369fad224`
4. **Client → server:** `conversation.item.create` (`function_call_output`, mocked result `{"time": "11:04 AM", "timezone": "CDT"}`) + `response.create`
5. **Server → client:** `response.output_text.delta` → `response.done`

> **dialog-rsn-1:** "It's 11:04 AM."

### 3. Cancellation mid-stream

1. **Client → server:** `response.create`
2. **Server → client:** `response.created` → a few `output_text.delta`
3. **Client → server:** `response.cancel`
4. **Server → client:** `response.done`, status `"cancelled"`. Any open output item closes as `incomplete`, so a client waiting on a matching `.done` isn't left hanging.
