The `instructions` parameter is your main lever over what Dialog-RSN-1 says and how it behaves: a system prompt, placed word for word into the model's prompt alongside your tools, your knowledge topics and the conversation so far. Nothing rewrites it. A `response.create` can add instructions for a single reply, and a platform content policy applies whatever your instructions say. This guide covers what that lever can and can't do. It starts with the one structural rule that catches most people out, then works through turn-taking, what the model hears, tool calling, response style, and how much of the context window your setup can take.

For something to paste rather than read about, start with the [prompt cookbook](/dialog-rsn-1/prompt-cookbook/introduction) instead.

## What it's tuned for

Dialog-RSN-1 is specialized for voice customer service, not general-purpose assistant work. It's good at taking a call, collecting details, calling your tools, and answering from your knowledge base. Push it toward an unconstrained task well outside that, and expect it to struggle in ways a general-purpose model wouldn't.

It answers in **English only** for now. More languages are coming in a model update.

<Note>
**You don't need to tell it what it is.** The default text style is already tuned for speech over a phone line, so an opening line like "you are a voice assistant talking to a caller on the phone" tells it something it already knows. Use that space for your business logic instead, and see [Response style](#response-style) for the parts worth overriding.
</Note>

## One output per turn

**Every model output is either text or a single tool call, never both.** Most prompts trip over this rule, because it changes what a two-part instruction like "say X and call Y" actually produces. The one thing that looks like an exception is a tool's [spoken argument](#speaking-while-a-tool-runs): Dialog-RSN-1 streams it as a message next to the call, but the model still wrote only the call.

The loop Dialog-RSN-1 expects is **tool → tool → … → text**. Emitting text is how it hands the floor back to the caller, so a turn ends when text comes out. Everything before that is tool calls, one at a time.

**There is no parallel tool calling.** To act on several tools, loop: call one, feed the result back with a `function_call_output` and a fresh `response.create`, and it calls the next. The [wire mechanics](/dialog-rsn-1/reference#function-calling) are the same on every pass.

### What "say X and call Y" actually does

Prompting for a spoken line *and* a tool call in the same response doesn't produce both. Dialog-RSN-1 resolves it in order: **it calls Y first, and its text comes in the response after the tool result.** By then the result has usually overtaken X, so expect the reply to report the outcome rather than say X word for word. That's deliberate rather than a failure to follow the instruction: a prompt like this is ambiguous about ordering, and picking one resolution consistently removes a class of bugs that would otherwise show up as the agent sometimes speaking first and sometimes not.

Write your instructions knowing the tool call goes first. If the caller needs to hear something before the tool runs, that's the next pattern.

### Speaking while a tool runs

**Since the model won't emit text and a tool call together, the hold line has to come from the call itself.** Give the tool an argument for it and mark that argument with `"poly_spoken": true`. The model fills it in as part of the call, in context, and Dialog-RSN-1 sends it to the caller as the call is written, before your tool runs.

<Warning>
**Without a spoken argument, a tool turn is silent until every tool call finishes.** The caller hears nothing through the whole chain, then the reply. With slow tools, this is the most common reason Dialog-RSN-1 seems slow in an existing agent or benchmark. Add a `poly_spoken` argument only to tools you expect to be slow, like an API lookup, or that do something the caller should hear about. List it in `required`: the model often leaves an optional one empty.
</Warning>

```json a tool schema with a hold-line argument
{
  "type": "function",
  "name": "look_up_booking",
  "description": "Look up a booking by reference number.",
  "parameters": {
    "type": "object",
    "properties": {
      "reference": { "type": "string" },
      "utterance": {
        "type": "string",
        "description": "A short line to say to the caller while this runs, for example 'let me pull that up for you'.",
        "poly_spoken": true
      }
    },
    "required": ["reference", "utterance"]
  }
}
```

The line arrives as the response's message, next to the `function_call` item. On a text session it streams as `response.output_text.delta` like any reply, so your text-to-speech speaks it with no extra code. When Dialog-RSN-1 speaks its own replies, it speaks the line. Either way, run the tool when `response.function_call_arguments.done` arrives, and the lookup happens while the caller hears the line.

The keyword must be `true`, on a `string` property, and on one property per tool at most, or the `session.update` is refused. The model never sees it: Dialog-RSN-1 removes it and adds "Spoken aloud to the caller while the tool runs." to the property's description. If the caller talks over the line, the model's copy of the call keeps only what they heard.

Leave it off fast tools and silent ones, like a tool that logs a detail, classifies the caller, or moves to another step of a flow. On a fast tool the line costs more than it saves: the answer can't start until the line has been said. In one test with a 300 ms tool, a required line brought first audio forward from 1.7 to 1.0 seconds but pushed the answer back from 1.7 to 3.0 seconds. On a tool that ends the call, put the goodbye in its spoken argument, for example a `closing_message` the prompt tells the model to use, and hang up on `response.done` with status `completed`, which waits for the line to finish.

### Getting at what the caller said, mid-loop

**The user transcript arrives after the text or tool call, not before it.** The reply is on the critical path and the transcript isn't, so it may simply not exist yet at the point in the loop where your harness wants it. See the [timing note](/dialog-rsn-1/reference#voice-input-and-transcription) in the reference.

So don't build harness logic that reads a number, a name, or a spelling out of the transcript mid-turn. **Pull it out as a function parameter instead:** declare the field on the tool and let the model fill it from what it heard. That's available the moment the arguments stream, it's already normalized to the shape your schema asked for, and it doesn't race the transcript.

## Turn-taking

Turn-taking is decided by the model, not a silence timer. The first token Dialog-RSN-1 emits is a verdict on the turn: **empty, ongoing, or complete**, judged against the full conversational context rather than the acoustics alone. Voice activity detection proposes the boundary; the verdict confirms or overrules it before anything reaches you.

That means there's no silence window to tune, and no threshold tuning to do for interruptions, hesitation, background noise, or an automated voice on the line. It also means the verdict is **promptable**, in plain language, the same as everything else.

<Warning>
**The realtime schema's turn-timing fields change nothing.** `silence_duration_ms`, `prefix_padding_ms`, `threshold` and `"type": "semantic_vad"` are accepted and left at this service's values, because the detector's thresholds are fixed, and `session.updated` echoes `server_vad` back. `interrupt_response: false` and `idle_timeout_ms` are refused with `unsupported_parameter`. `turn_detection: null` turns detection off for push-to-talk, and your client then decides where every turn ends. `create_response` is the only field of `turn_detection` this service reads. Tune turn-taking in `instructions` instead. See the [reference](/dialog-rsn-1/reference#turn-taking-and-audio).
</Warning>

### What prompting can't do

Prompting can't make Dialog-RSN-1 cut in while the caller is still talking. Barge-in runs one way only: a caller starting up again cancels an in-flight response, covered in [the overview](/dialog-rsn-1/overview#turn-taking). Nor does prompting change the loop shape above: text still ends the turn.

### Patterns

#### Treating a short turn as incomplete

**A pause mid-answer looks like the end of a turn unless you say otherwise.** Callers with more than one thing to say, several items in an order, more than one date, seldom get through it in one breath.

Say what "complete" looks like, and what to do when a pause ends the turn short of it: ask "anything else?" rather than act on the first item. The caller gets the floor straight back instead of an agent that has already moved on.

Recipe: [prompt cookbook](/dialog-rsn-1/prompt-cookbook/turn-taking#waiting-for-a-complete-sequence).

#### Breaking from the default path when a caller is stuck

**Repeating the same request after a caller has struggled with it twice reads as the agent not listening.** `instructions` can name the fallback: after a set number of failed attempts at collecting a postcode, offer to look the account up another way.

Recipe: [prompt cookbook](/dialog-rsn-1/prompt-cookbook/turn-taking#offering-a-fallback).

## What the model hears

Dialog-RSN-1 hears the call, not a transcript handed to it after the fact. Two things follow from that, and both are easy to get wrong from the outside.

### Send raw audio

**Dialog-RSN-1 always sees the raw audio, and feeding it enhanced audio degrades performance.** Noise suppression, aggressive gain control, and similar pre-cleaning strip exactly the cues the model is trained to use. Don't clean the signal up on the way in.

### Ground hard nouns

A name or a drug the model has no reason to expect gets transcribed as whatever it sounds closest to, not as itself. **Put the list it needs in `instructions`, spelled the way you want it recognized, and the model only has to get close rather than exact.** This is fusion working in your favor: because transcription and generation are one pass, a garbled acoustic signal resolves toward whatever `instructions` already told it was plausible.

```text instructions: ground names against a known list
The caller may ask for one of these doctors: Dr. Nikola Mrksic, Dr. Amara
Okafor, Dr. Liu Wei. The caller may name one of these medications:
Metoprolol, Lisinopril, Atorvastatin. If what you hear is close to one of
these names, resolve it to that name and say it back the way it's spelled
here, regardless of how it sounded.
```

"Mrksic" heard down a phone line resolves to "Nikola Mrksic" once it's a known option instead of a name from nowhere, and "me-tap-ro-LOL" resolves to "Metoprolol" the same way. This works best on a list that's realistically confusable and doesn't change every call, a roster or a formulary rather than one caller's personal contacts. Recipe: [prompt cookbook](/dialog-rsn-1/prompt-cookbook/grounding#grounding-hard-nouns).

### Prompt for the behavior, not the classification

The model perceives a lot more than words: gender, language, accent, emotion and tone, background noise, telephony artefacts, and whether the voice on the line is a person or a machine. On outbound calls it's trained on the conditions that matter there too, a human answering versus an IVR, voicemail and its beep, hold, silence, transfer cues, and spoken menu options.

**Prefer to prompt for the behavior you want directly, rather than asking for a label and branching on it in your harness.** For example:

```text instructions: react to a noisy line
Do your best to answer the caller's questions even if the line is noisy.
If you can't make out what they're saying, tell them what you're hearing
and ask them to move somewhere quieter or repeat themselves, then carry on.
```

If you'd rather track a condition as explicit state, the alternative is to **have the model call a function to classify it**: declare a tool like `report_line_condition(condition, confidence)` and branch on the arguments in your harness. That costs a round trip in the loop, so reach for it when your side genuinely needs the state, not just the behavior.

#### Reacting to what a transcript would miss

**A sneeze, or a "hang on" muttered mid-sentence, is something a text-only pipeline drops entirely.** When it happens during the caller's turn, `instructions` can ask Dialog-RSN-1 to acknowledge it in passing, a "bless you" before it answers. While a reply is playing, the words can't change: a sound the model judges to be no speech is ignored and the reply plays on, and anything else interrupts it. There, `instructions` shape that judgment rather than the reply.

Recipe: [prompt cookbook](/dialog-rsn-1/prompt-cookbook/turn-taking#acknowledging-what’s-not-a-word).

## Tool calling

A tool's `description` and `parameters` tell Dialog-RSN-1 what the tool does and what it needs. They don't tell it when calling is worth the round trip, or how to talk about a result once it has one. That judgment lives in `instructions`, alongside everything else in this guide.

The mechanics are fixed and not promptable: arguments stream in, you run the tool, you add a `function_call_output`, you send a fresh `response.create`. That's [wiring, not judgment](/dialog-rsn-1/reference#function-calling), and it works the same regardless of what `instructions` says. What `instructions` controls is everything upstream and downstream of it, on top of the [loop rules above](#one-output-per-turn).

### Patterns

#### Confirming before anything that can't be undone

**A tool that cancels a booking or charges a card shouldn't fire on the first thing that sounds like a yes.** Nothing in the protocol distinguishes a read-only tool from a destructive one, since `tools` only carries a name, a description, and a parameter schema, not a risk level.

That distinction has to live in `instructions`: name the tools that need a spoken confirmation first, and say so explicitly, rather than trusting the model to infer which ones are risky from their names alone. Recipe: [prompt cookbook](/dialog-rsn-1/prompt-cookbook/tool-calling#confirming-before-anything-that-can’t-be-undone).

#### Speaking naturally about a result, not the tool that produced it

**"Calling get_weather now" is a debugging log line, not something a caller on a phone call wants to hear.** Left unguided, a model narrating its own tool use tends to describe the mechanism instead of the outcome.

Redirect that in `instructions`: talk about what was found, not what was called. Recipe: [prompt cookbook](/dialog-rsn-1/prompt-cookbook/tool-calling#speaking-about-results-not-tools).

#### Handling a tool that came back with an error

**A `function_call_output` is just a JSON string you wrote. Nothing about the protocol flags it as an error for you.** Even a stale or mismatched `call_id` raises no error: the result is kept as an item but left out of the model's input. A business-logic failure inside a successfully matched result, an account not found, a payment declined, looks identical to a success from the wire's point of view.

Whatever error shape your tools return, `instructions` has to describe it, or Dialog-RSN-1 has no way to tell "done" from "failed" apart. Recipe: [prompt cookbook](/dialog-rsn-1/prompt-cookbook/tool-calling#handling-a-tool-error).

#### Searching, and getting citations back

**Search is a tool like any other; the passages it finds come back in a field of their own.** Dialog-RSN-1 does no retrieval itself. Declare a search tool the same way you'd declare any other function:

```json declaring a search tool
{
  "type": "function",
  "name": "search_knowledge_base",
  "description": "Search the knowledge base for passages relevant to the caller's question.",
  "parameters": {
    "type": "object",
    "properties": { "query": { "type": "string" } },
    "required": ["query"]
  }
}
```

When the model calls it, your harness runs the actual search and attaches what it found as [`poly_knowledge`](/dialog-rsn-1/reference#the-session-object) on the `function_call_output`, a list of `{name, content}` topics, alongside whatever `output` you'd normally return:

```json answering the search with retrieved topics
{
  "type": "conversation.item.create",
  "item": {
    "type": "function_call_output",
    "call_id": "call_abc123",
    "output": "{\"found\": 2}",
    "poly_knowledge": [
      { "name": "refund_policy", "content": "Refunds are issued within 5 business days of approval." },
      { "name": "return_window", "content": "Items can be returned within 30 days of delivery." }
    ]
  }
}
```

A topic can also carry `actions`, an optional string. Send it as a string, not a list: a list fails validation with `invalid_request_error` and the whole item is refused. Validate the shape in your harness before you send it, because a refused result still uses up the call. A corrected resend with the same `call_id` is accepted but left out of the model's input, with no error.

Send a fresh `response.create` after that, same as any other tool result. Dialog-RSN-1 renders those topics into one numbered list to cite into, and the reply's `response.done` carries `poly_cited_topics`: the names of the topics it actually answered from, absent rather than empty when it cited none. `instructions` is where you say when to search rather than answer from memory, and what to do when the search comes back with nothing relevant. Recipe: [prompt cookbook](/dialog-rsn-1/prompt-cookbook/tool-calling#searching-and-getting-citations-back).

## Response style

The model writes every reply as text, and then the API or your own text-to-speech speaks it. With your own text-to-speech you can log, test and guardrail a reply before the caller hears it, as the [overview](/dialog-rsn-1/overview#the-core-split) explains.

**The default style already accounts for that.** Out of the box it writes plain spoken sentences, not screen-native prose with headings and bullets, so you don't need to spend a paragraph of `instructions` ruling markdown out. Style is fully overridable when you need something specific, and these are the overrides worth making.

### Patterns

#### Saying numbers, dates, and times the way a person would

**"14.99" is unambiguous on a screen. Read literally, it can come out as "fourteen point nine nine" instead of "fourteen dollars and ninety nine cents."** Both are valid readings of the same characters, so the convention you want is worth stating.

Spell it out in `instructions` for the kinds of numbers your agent actually says: prices, dates, phone numbers, confirmation codes. Recipe: [prompt cookbook](/dialog-rsn-1/prompt-cookbook/response-style#saying-numbers-the-way-a-caller-expects).

#### Keeping replies short enough to say in one breath

**Voice has no skim button, so length that would be fine in chat is not automatically fine here.** `output_text.delta` streams incrementally and most setups start speaking before generation finishes, so a long front-loaded sentence also delays the moment a caller hears anything at all.

Set an explicit ceiling, a sentence count or a rough word budget, rather than leaving brevity to a judgment call. Recipe: [prompt cookbook](/dialog-rsn-1/prompt-cookbook/response-style#keeping-replies-short).

#### Tagging a reply with an emotion for your TTS

**If your text-to-speech takes a style or emotion input, the model can pick one per reply.** Offer a set of tags in `instructions` and ask for the answer prefixed with one in square brackets; strip the tag off in your harness before the text reaches the synthesizer, not after. Skip that step and the caller hears the bracket and the tag word read aloud, right before the reply itself.

```text instructions: prefix each reply with an emotion tag
Choose ONE emotion tag for your response from: [friendly], [apologetic],
[reassuring]. Return your answer prefixed with the tag in square brackets.
```

```text a reply
[reassuring] Don't worry, I can get that sorted for you.
```

The tags aren't a fixed enum, and the model generalizes to ones you invent. Common choices are `[friendly]`, `[energized]`, `[reassuring]`, `[empathetic]`, `[apologetic]`, `[patient]`, `[confident]`, `[assertive]`, `[diplomatic]`, and `[informative]`. A response that's only a tool call carries no tag, since it emits no text to prefix, so parse the prefix as optional. Recipe: [prompt cookbook](/dialog-rsn-1/prompt-cookbook/response-style#tagging-a-reply-with-an-emotion).

## Fitting the context window

**Keep your `instructions` and `tools` under about 20,000 tokens together, so the conversation has room to grow.** The [context window](/api-reference/dialog-rsn-1/limits) is 32,768 tokens, audio included. Every reply's prompt holds your `instructions`, every tool definition, and the conversation so far.

Only the conversation gets smaller as a call goes on. From the tenth caller turn, older turns give up their audio and keep their transcript. Your `instructions` and `tools` go into every prompt in full, on every turn, and nothing compacts them. A setup of 28,000 tokens leaves about 4,000 for the call itself, which a few turns use up.

When a prompt outgrows the window, that response fails with `context_length_exceeded`: an `error` event, then a `response.done` with `status: "failed"`. The connection stays open. A `session.update` with oversized `instructions` is accepted without complaint, so the first sign is the first reply failing.

### Measuring your setup

**Read `response.usage.input_tokens` off the first reply.** Send your `session.update`, one short user message and a `response.create`, then check the number on `response.done`. That count is the fixed cost every later turn starts from.

For a rough estimate before you send anything, count about four characters of English per token, and about 100 tokens for a tool with a one-line description and two parameters. Some measured first replies:

| Setup | `input_tokens` |
| --- | --- |
| 270 characters of instructions, no tools | 392 |
| The same instructions, 20 tools | 2,477 |
| 13,550 characters of instructions, no tools | 3,136 |
| 108,400 characters of instructions, no tools | 22,736 |

### When you're over

- **Cut what the model doesn't need on every turn.** Long policy text, FAQs and product lists cost their full size on every reply.
- **Move reference material behind a search tool.** Return the passages as [`poly_knowledge`](#searching-and-getting-citations-back) on the tool result, so only what the caller asks about enters the prompt.
- **Declare fewer tools.** Merge tools that take the same arguments, and drop the ones this agent never calls.
- **Split the call into stages.** Give each stage its own `instructions` and `tools`, and swap them in with `session.update` as the call moves on. The history stays intact. The [realtime agents example](https://github.com/polyai/dialog-rsn-1-realtime-agents) does this for handoffs.
